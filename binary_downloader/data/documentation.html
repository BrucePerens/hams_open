Binary Downloader Facility

The Binary Downloader is a secure system that provides technical dependencies (helper programs) like kopia (for backups), etcd (for distributed configuration), or cloudflared (for secure tunnels) to Odoo automatically.

1. Purpose and Automation

Modern Odoo deployments often rely on external high-performance tools written in languages like Go or Rust. Instead of requiring manual system administration to install these tools on the host server, the Binary Downloader automates the lifecycle of these dependencies. This module operates without administrative privileges (Zero-Sudo: this platform's rule that code never calls Odoo's .sudo(); privileged steps run as a dedicated service-account user instead) and ensures that all binaries are verified for integrity before execution.

When an Odoo module needs a specific program, it asks the Binary Downloader to "ensure" it is available. If the program is missing or invalid, it is downloaded, verified for integrity using cryptographic hashes, and installed into a protected internal directory. This request always uses the copy in that directory, never a same-named program found on the system PATH.

2. Operating the Module

While most operations happen automatically when other Odoo modules require them, administrators can monitor, configure, and trigger installations manually. This module supports both system-wide "Manifests" (simple, automatic) and fine-grained "Tenant Versions" (advanced control).

2.1. Monitoring and Manual Installation

  1. Open the Binary Manifests menu. It is declared as a top-level menu (no parent), not under Settings -> Technical.
  2. Review the list of binaries. The Installed column indicates if the dependency is currently available on the system PATH or in Odoo's private binary directory (hams_bin).
  3. To manually install or update a dependency, click the Install button on the list view, or open the record and click Install Now. These buttons are shown only to members of the Binary Downloader Manager group and administrators, and only while the binary is not marked Installed. A program found on the system PATH counts as Installed, so its button is hidden.
  4. If an installation fails, a detailed notification will explain the cause (e.g., network error, checksum mismatch, or missing member in archive).

2.2. Versioned Binaries and Tenant Assignments

In advanced multi-tenant environments, you may need different websites to use different versions of the same tool.

  1. Version Management: Under Settings -> Technical -> Version Pool, you can define multiple specific releases for a Software Manifest (e.g., Kopia 0.12.1, 0.13.0).
  2. Central Pool UI: From the Version record, click Download to Pool to retrieve the selected binary version and store it in the central pool. The central pool is the same protected hams_bin directory manifests install into; each version is stored there under a name derived from its binary name and checksum. Only members of the Binary Downloader Manager group and administrators may download.
  3. Station Notification: Use the Alert Stations via PagerDuty button to trigger automated alerts to stations when a new version becomes available. "PagerDuty" here is this platform's own Pager Duty module: the button creates one incident, of medium severity, for each website linked to this software that is not already on this version. Only members of the Binary Downloader Manager group and administrators may send alerts.
  4. Tenant Links: Under Settings -> Technical -> Station Executables, you can link a specific Tenant / Website to a Software and select an Active Version. A tenant, a station and a website mean the same thing here. Each website can have one link per software. The 1-Click Upgrade to Latest button switches the link to the version with the latest Upstream Release Date.
  5. Automatic Symlinks: The system automatically creates a secure "shortcut" (symlink) in a website-specific directory (tenant_bins/site_ID/). This allows your website-specific scripts to always find the correct version of the tool. The symlink is created when the link is saved and re-pointed when the Active Version changes; a version not yet in the central pool is downloaded first.

2.3. Adding New Binaries

If you need to add a new tool for a custom module:

  1. Click the New button in the Binary Manifests list.
  2. Binary Name: Enter the command name (e.g., my-utility). Do not use slashes or backslashes.
  3. Company: Select the company that owns this manifest. In multi-company environments, this ensures that each company can have its own specific version or download source for a binary.
  4. Download URL: Provide the HTTPS link to the raw binary or the .tar.gz or .zip archive. Only https:// URLs are accepted.
  5. SHA-256 Checksum: Provide the expected SHA-256 hash of the file. This is mandatory for security.
  6. Archive Type: Select "Raw Binary" if the URL points directly to the executable, "Tarball (.tar.gz)" for Gzipped Tar archives, or "Zip Archive (.zip)" for ZIP files.
  7. Extract Member: For tarballs and zip files, specify the filename within the archive that should be extracted as the executable. This is required for .tar.gz and .zip files. The first archive entry whose path equals this value, or ends in / followed by it, is used, so a file inside a subdirectory can be named by its file name alone.

3. Security Architecture

Security is at the core of the Binary Downloader design:

  • Cryptographic Verification: Every downloaded file is verified against a SHA-256 checksum. If the file's digital fingerprint doesn't match the expected value, the installation is aborted to protect against tampering.
  • Advisory Locking: The system uses database-level locks (PostgreSQL advisory locks) to ensure that multiple Odoo workers don't try to install or update the same binary simultaneously, preventing file corruption.
  • Micro-Privilege: Downloads and installations are performed using a restricted service account (user_binary_downloader_service) to minimize system risk, adhering to the Zero-Sudo mandate.
  • Path Sanitization: Strict protections are in place to prevent "Tar Slip" and "Zip Slip" vulnerabilities, in which a path such as ../../x inside an archive makes extraction write outside the intended directory. Only the one selected archive member is extracted, and it is always written to a file name the system computes, never to the path stored in the archive. Symbolic links and hard links within archives are strictly forbidden: if the selected member is a link, installation is refused.
  • Isolation: Binaries are stored in a dedicated hams_bin folder within Odoo's data directory, kept separate from system-wide binaries and set with restricted 0o750 permissions.

4. Troubleshooting Common Issues

  • Checksum Failures: If you see a "Security Alert: Checksum mismatch", it means the file downloaded from the internet does not match the fingerprint in Odoo's database. This could be due to a corrupted download or a change in the remote file. Contact your technical support.
  • System Architecture: Automatic installation runs only on Linux on x86_64, aarch64 or armv7l processors; on anything else it stops with an error asking for manual installation. The manifests shipped with this module (kopia, etcd, cloudflared) point at 64-bit x86 (x86_64) Linux builds, so on other processors change their Download URL and checksum to a matching build. They are shipped from the module's data file, so a module upgrade resets those three manifests to the shipped values and undoes such an edit. A company-specific manifest of the same name is not reset and takes precedence over the shipped global one for that company.
  • Network Connectivity: The Odoo server must have HTTPS access to the download URLs (e.g., github.com) to fetch the dependencies. A mirror can be used by pointing a manifest's Download URL at it, but only if its host name resolves to public internet addresses: loopback, private-network and other internal addresses are refused (also after a redirect) to stop the server being used to reach internal services. Downloads over 1 GiB are refused, and network operations use a 15-second timeout.
  • Missing Member: For archives, ensure the "Extract Member" field exactly matches the filename inside the archive.
  • Permissions: If a binary is present but not executable, the system will attempt to set its permissions to 0o750. Ensure Odoo has write access to its own data directory.
