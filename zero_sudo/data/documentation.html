Zero-Sudo Security: User Guide

The zero_sudo module is the foundational security layer of the platform. It enforces a "Zero-Sudo" policy, ensuring that background tasks and automated processes operate with minimal, strictly-defined permissions.

Key Security Features

Service Accounts

A "Service Account" is a special user profile created for automated tasks (like sending emails or backing up data). These accounts are hardened to prevent misuse:

  • Web Login Block: Service Accounts are strictly forbidden from logging in through a web browser. Any attempt to do so is instantly blocked; a sign-in with the correct password is also logged for auditing before the session is ended.
  • Automated Hardening: Every Service Account is assigned a complex, randomized password that is impossible to guess, ensuring only the intended automated system can use it. Turning the checkbox on or off replaces the password with a new random one, and later password changes to a Service Account are ignored.
  • How to Identify: You can manage these accounts in Settings > Users & Companies > Users by toggling the "Is Service Account" checkbox on the Access Rights tab. Only Settings administrators can see or change it.

Safe Configuration & Parameter Whitelisting

To prevent sensitive data leaks, the system uses a strict whitelist for configuration parameters. Parameters like encryption keys or master passwords cannot be accessed or modified through the security core's parameter helpers, which background programs use, unless they are explicitly registered in the security core. A refused read or write is logged. This protects against several classes of system-level attacks.

Centralized Security Logs

The system maintains a centralized audit trail for critical security events. Administrators can monitor these in Settings > Zero-Sudo Security > Security Audit Logs. Tracked events include:

  • Blocked Login Attempts: When a Service Account signs in to the web UI with its correct password.
  • Privilege Escalation Violations: A reserved event type for an automated process attempting to gain full system administrator rights. Nothing in this repository currently records it; the attempt is refused with an access error instead.
  • Restricted Parameter Access: When an unauthorized attempt is made to read or write sensitive system configurations (reads and writes are recorded as separate event types).
  • Cache Invalidation: Records a manual refresh of the cached data for one kind of record (one model), not the whole system.

Safe Cache Invalidation

To optimize performance without compromising security, the system provides a granular way to refresh data caches. Users with appropriate permissions (write access to that kind of record) can safely trigger a refresh for specific parts of the system, ensuring that data is always up-to-date without needing full administrative rights. This prevents "stale data" issues while maintaining strict isolation between different parts of the platform.

Noisy Table Management

System administrators can flag specific technical tables as "Noisy" in Settings > Zero-Sudo Security > Noisy Tables. Noisy tables are ignored by the Real Transaction Testing Facility's end-of-test database leak check (see the Real Transaction Testing Facility Guide). This reduces false test failures for tables that are known to have high-frequency data changes from background processes.

Frequently Asked Questions

"I get an 'Access Denied' error when logging in!"

If you see an error referring to access_denied_service, you are trying to log in with a Service Account. These accounts are for background tasks only. Please use your standard employee account.

"Where are the system manuals?"

This module automatically installs and updates help guides like this one each time the server loads, whenever a guide's content has changed. You can find them in the Knowledge app, if it is installed. Guides are visible only to administrators unless a module marks them as public.
