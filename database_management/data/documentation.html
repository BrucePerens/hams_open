Database Management & SRE Toolkit Guide

The Database Management module is a comprehensive suite designed for Site Reliability Engineers (SREs) and Database Administrators (DBAs). It allows for deep monitoring, performance tuning, and high-availability orchestration of the PostgreSQL database directly from within Odoo.

Getting Started

All database management features are located under the Database & SRE main menu. Access is strictly limited to users with System Administrator privileges to ensure the security and integrity of your data. System Administrators automatically hold the Database Manager group, which is the group the rest of this guide refers to.

1. Monitoring Table Health & Bloat

Database "bloat" occurs when many records are updated or deleted, leaving behind "dead tuples" that still occupy disk space. Over time, this can significantly slow down your system.

How to identify bloat:

  1. Go to Database Health > Table Health & Bloat.
  2. Look at the Dead % column. A value over 20% generally indicates that the table could benefit from a manual cleanup.
  3. The Cache Hit % indicates how much data is being read from memory vs. disk. Higher is better (ideally > 95%).

How to reclaim space:

  1. Select the tables you wish to clean in the list view.
  2. Click Vacuum Analyze Selected. This triggers the PostgreSQL VACUUM ANALYZE command, which removes dead tuples and updates optimizer statistics.
    Performance Note: The system automatically batches these requests to minimize overhead: all selected tables are cleaned by a single vacuumdb run. If that run fails or takes longer than 10 minutes, an error message is shown.

Index Advisor:

Tables that are large and have many sequential scans are prime candidates for new indexes.

  • Navigate to Database Health > Index Advisor.
  • The advisor lists tables with more than 100 sequential scans that are larger than 10 MB, most-scanned first. It does not propose a specific index. Review these and consider if adding an index on columns used in WHERE clauses or JOINs would improve performance.

Security Note: Vacuuming is an intensive operation. Only users with Database Manager privileges can trigger it.

Proactive Alerting: The system automatically monitors these levels and will trigger a PagerDuty incident if critical tables exceed safe bloat thresholds. Once a day, any table with more than 20% dead tuples and more than 10,000 dead tuples is listed in one incident. (PagerDuty here means this system's own Pager Duty module.)

2. Index Health & Usage

Indexes speed up read operations but slow down writes and consume disk space. Unused indexes should be removed.

  • Navigate to Database Health > Index Health.
  • The Total Scans column shows how often an index is actually used. If a large index has zero or very few scans, it may be a candidate for removal. Indexes with zero scans are highlighted. Unique indexes (including primary keys) are not listed.

3. Slow Query Tracking (APM)

Application Performance Monitoring (APM) is built-in to help you find the "heaviest" queries hitting your database.

  • Go to Database Health > Slow Queries (APM).
  • Queries are sorted by Total Time. This helps you identify which parts of the application are causing the most load, even if individual executions are fast.
  • Installation Note: If queries do not appear (the list shows a single row saying pg_stat_statements is not installed or not loaded), you may need to install the pg_stat_statements extension. Ensure it is included in your postgresql.conf shared_preload_libraries, restart PostgreSQL, and then use the Install / Fix Extension button to enable it on the database.
  • Reset Statistics: There is currently no Reset Statistics button in this view. The server-side method that clears the statistics exists but is not connected to the interface.
  • Explain Plan: Click the Explain (search icon) next to a query to generate a detailed EXPLAIN (ANALYZE, BUFFERS) plan. Only queries starting with SELECT or WITH are accepted; any other query is refused with an error. This reveals exactly how PostgreSQL is executing the query and where the bottlenecks are.

4. Active Sessions & Kill Switch

Sometimes a single "runaway" query or a deadlocked session can freeze parts of the system.

  • Go to Database Health > Active Sessions.
  • Review the Duration and the Active Query text.
  • Sessions whose Duration (time since their current or most recent query started) is over 60 seconds are highlighted in red.
  • If you identify a process that is causing issues, select it and click Kill Selected Queries. This safely terminates the database backend for that specific session.

Security Note: Terminating sessions can interrupt user operations. Only Database Managers are authorized to use this feature.

5. Replication Monitoring

For systems with standby nodes, monitoring replication lag is critical to ensure data consistency and high availability.

  • Navigate to Database Health > Replication Monitoring.
  • The view shows connected standby nodes, their state, and Replay Lag.

6. Performance Optimization Wizard

Configuring PostgreSQL for Odoo can be complex. Our wizard automates this using industry-standard DBA formulas.

  1. Go to Database Health > Configuration & Tuning > Optimization Wizard.
  2. Enter your server's Total RAM and CPU Cores.
  3. Select your storage type (SSD is highly recommended) and the Max Connections you need (default 200).
  4. Click Calculate & Apply Optimizations.

The formulas, with RAM in MB: shared_buffers = 25% of RAM; effective_cache_size = 75% of RAM; maintenance_work_mem = 5% of RAM, at most 1024 MB; work_mem = 25% of RAM divided by Max Connections, at least 4 MB; random_page_cost = 1.1 for SSD or 4.0 for HDD; max_worker_processes and max_parallel_workers = CPU Cores; max_parallel_workers_per_gather = half the CPU Cores, at least 2; max_connections = the value entered. They are written with ALTER SYSTEM (into postgresql.auto.conf) and the configuration is reloaded.

Note: Some settings (like shared_buffers) require a full PostgreSQL service restart to take effect. The wizard always shows a reminder about this after applying; it does not restart PostgreSQL. The Pending Restart column in Configuration & Tuning > View Active Settings shows which settings are still waiting for a restart.

7. High Availability (HA) Orchestrator

For production environments requiring high availability, this tool generates configuration templates for Patroni (including its etcd connection settings) and PgBouncer: one Patroni YAML file per node, which connects Patroni to your existing etcd hosts, and one PgBouncer INI file. It does not generate etcd's own configuration.

  1. Go to Database Health > Configuration & Tuning > High Availability Orchestrator.
  2. Enter the IP addresses for your Primary and Secondary nodes, the cluster name, and the etcd hosts as comma-separated host:port pairs.
  3. Set a strong Replication Password (minimum 8 characters, with no characters that would break the YAML file). A random password is filled in by default. The generated Patroni files use this same password for both the replication user and the superuser.
  4. Click Generate Configurations to receive tailored YAML and INI files for your cluster nodes. They are shown in three tabs for you to copy; nothing is installed or deployed. The patroni, pgbouncer and etcd programs must be available on the Odoo server; if one is missing, the system tries to install it through its binary downloader, and otherwise generation stops with an error.

Security & Architecture

To maintain a "Zero-Sudo" environment (this system's rule that Odoo's sudo() shortcut is never used), this module uses a dedicated service account (user_database_management_service) for sensitive operations: killing sessions, resetting query statistics and generating Explain plans. The Optimization Wizard's settings changes and Vacuum do not go through this account. This ensures that even administrative actions are performed with the minimum necessary privileges and are fully auditable.

Multi-Tenant Considerations

Models in this module are classified as logically global. This is because they interface directly with PostgreSQL system views that track the health and activity of the entire current database (and, for replication, the whole PostgreSQL server) rather than of one company. In a multi-company setup, these metrics provide a unified view of the shared database resources, ensuring that administrators can optimize performance for all users simultaneously.
