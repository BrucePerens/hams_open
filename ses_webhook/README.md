# SES Webhook Receiver

## Overview
A module to securely receive Amazon SNS (Simple Notification Service) webhooks containing SES incoming emails. It routes emails to the appropriate tenant company within Odoo by passing them to `mail.thread.message_process`.

## Developer Guide

### Key Components
- **`SesWebhookController` (`controllers/webhook_api.py`)**: Defines a public HTTP endpoint at `POST /mail/webhook/sns`. It receives incoming Amazon SNS webhooks.
  - **Authentication (two independent layers, both required)**: (1) a per-domain URL query parameter `token`, matched against `ses.webhook.domain.secret_token`; (2) real AWS SNS message-signature verification (`_verify_sns_signature`) -- the request body's own `Signature`/`SigningCertURL`/`SignatureVersion` fields are checked against AWS's documented signing scheme (the canonical string-to-sign built per the message's `Type`, verified against the certificate fetched from `SigningCertURL` after confirming that URL is a real `sns.<region>.amazonaws.com` signing-cert host). A request failing either check is rejected with 403; a signature failure on an otherwise-valid token is logged with its own `rejected_signature` status for forensic visibility (a valid token but a forged/unsigned message is the exact scenario a leaked token alone can no longer forge).
  - **Request shape**: after a valid token, an empty body, a body that is not JSON, or JSON that is not an object is rejected with 400. A request with a missing or wrong token is rejected with 403 and is not written to the log (there is no domain to attach it to).
  - **Subscription Confirmation**: Automatically confirms SNS subscription requests by visiting the `SubscribeURL`, but only when that URL is an `https://sns.<region>.amazonaws.com/` address. Any other `SubscribeURL` is not fetched, and the log entry gets status `rejected_subscribe_url`.
  - **Notification Processing**: Parses SES notifications. If a valid `content` field containing a raw email is found, it encodes the email in UTF-8 and feeds it into the standard Odoo mail thread message_process method for the matched company. The other outcomes:
    - **Bounce / Complaint**: an SES event notification (`notificationType` of `Bounce` or `Complaint`) carries no `content`; its recipient addresses are added to Odoo's `mail.blacklist`, so later outbound mail to them is suppressed. Every complaint is suppressed; a bounce is suppressed only when its `bounceType` is `Permanent`, because a transient bounce (for example a full mailbox) may succeed later.
    - **No content**: a Notification with no `content` field is logged with status `ignored`.
    - **Unmatched sender**: before calling `message_process`, the sender address is parsed and matched to a user. If no user matches, `message_process` is not called; the email is held as a `ses.webhook.pending_submission` record, the sender is emailed a link to register and asked to resend, and the log status is `ignored`. (`message_process` itself would otherwise create the record anyway, attributed to the calling account.)
    - **Processing error**: any exception during processing is logged with status `failed`, and the response is still HTTP 200, because SNS keeps retrying a delivery that gets a non-2xx response.
  - **AWS SNS signature verification** (`[@ANCHOR: ses_webhook:COMM_verify_sns_signature]`): infrastructure/plumbing, not a user-facing feature -- verifies `Signature` against the string-to-sign AWS documents for the message's own `Type`, using the certificate `[@ANCHOR: ses_webhook:COMM_fetch_sns_signing_cert]` fetches (and caches) from `SigningCertURL`. Fails closed on any missing field, non-AWS cert host, unreachable/expired certificate, unsupported `SignatureVersion`, a signed `Timestamp` more than 15 minutes away from the current time (replay defense: the signature proves AWS signed the message once, not that this delivery is the first), or signature mismatch.
- **`SesWebhookDomain` (`models/ses_webhook_domain.py`)**: Stores the domain name and maps it to a specific tenant company (`res.company`).
  - Auto-generates a secure `secret_token` upon creation.
  - Computes the webhook URL: the server's `web.base.url` plus `/mail/webhook/sns?token=<secret_token>`. The token travels in the URL, so the URL must be kept private.
  - Creating a domain, or changing its company, adds that company to the allowed companies of the module's service account (`ses_webhook.user_ses_webhook_service_internal`). The controller does its token lookup, logging and pending-submission writes as that account rather than with `.sudo()`, and an account that is not `.sudo()` can only switch into a company it belongs to. (The one `.sudo()` call is the final `message_process` for a matched sender: `message_process` elevates internally on any alias match anyway, and the sudo environment is what lets it attribute the new record to the matched sender.) The service account's own record rules let it reach every tenant's domain, log and pending-submission records regardless of company, because the token lookup happens before the company is known.
- **`SesWebhookLog` (`models/ses_webhook_log.py`)**: Logs webhook activity (Payload Type, Status, Raw Payload, Error Messages). Status is one of `success`, `failed`, `ignored`, `rejected_subscribe_url`, or `rejected_signature` (a valid token whose message failed AWS signature verification).
  - **Scheduled Action**: `_cron_truncate_logs` runs daily to remove logs older than 30 days to save database space (at most 10,000 rows per run).
- **`SesWebhookPendingSubmission` (`models/ses_webhook_pending_submission.py`)**: Holds the raw email of a sender with no matching user (see Unmatched sender above), with its domain, company and a random `token`. The `consumed` flag exists for a future flow that links a newly registered user back to the held email; nothing sets it yet. A daily scheduled action, `_cron_truncate_pending_submissions`, deletes these records 7 days after creation, consumed or not, since they hold unauthenticated email content.

### Usage
Developers extending this module do not typically need to call its functions directly. Instead, this module acts as an ingestion pipeline into the standard `mail.thread` mechanism. Developers should rely on the standard Odoo `message_new` and `message_update` methods in their models to process the ingested emails.
