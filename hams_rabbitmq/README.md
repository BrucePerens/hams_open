# Hams RabbitMQ

The `hams_rabbitmq` module provides a global RabbitMQ Connection Pool via an abstract model `hams_rabbitmq.pool`. This enables other modules to safely publish messages to a RabbitMQ broker using Odoo's environment.

"Pool" here means one shared connection, not a set of them: the model keeps a single RabbitMQ connection and a single channel as class attributes, guarded by a lock, and every caller reuses them. A closed connection is reopened, and a closed channel is replaced on the still-open connection, on the next use.

## Developer API

### Abstract Model: `hams_rabbitmq.pool`

Developers can inherit or call the abstract model to publish messages:
`self.env['hams_rabbitmq.pool'].publish(exchange, routing_key, body, properties=None, on_result=None)` ([@ANCHOR: rabbitmq_publish]).

`publish()` always returns `True` meaning only "queued for after commit". To learn whether the real AMQP (Advanced Message Queuing Protocol, the wire protocol RabbitMQ speaks) send succeeded, pass `on_result`, a callable invoked as `on_result(success: bool)` from the postcommit hook after the send is attempted; it runs after commit (open your own cursor if it must write) and its exceptions are logged, never raised.

A `dict` body is serialized to JSON before sending; any other body is passed through unchanged. If `properties` is omitted, the message is sent as persistent (`delivery_mode=2`). If no channel can be obtained, or `basic_publish` raises an AMQP error, the message is dropped: the failure is logged with its exchange and routing key, `on_result(False)` is called, and after a broker error the connection is discarded so the next publish reconnects. The one exception is a dead pooled connection, which is retried once as described below.

A pooled connection the broker has dropped since it was last used (broker restart, heartbeat timeout, its user deleted) fails on first use, typically with `StreamLostError` ("Connection reset by peer"). The send then discards that connection ([@ANCHOR: rabbitmq_discard_stale_connection]) and retries exactly once on a freshly opened one, logging a warning. Only if the retry fails too does `on_result(False)` fire. A refusal on a live channel (e.g. `UnroutableError`) is not retried.

### Keepalive, idle and inherited connections
pika's `BlockingConnection` answers the broker's heartbeats only while the process is inside a pika call, so a pooled connection that sits idle between publishes goes silent and the broker resets it ("missed heartbeats from client", heartbeat timeout 60 s; 262 such closes in three days in production before the keepalive).

**Keepalive** ([@ANCHOR: rabbitmq_keepalive_thread]). When the pool opens a connection it starts, lazily, one daemon thread per process (`hams_rabbitmq_keepalive`). The thread body is a loop that waits on a stop `Event` with a `KEEPALIVE_SECONDS` timeout and returns as soon as a tick reports there is nothing left to keep alive ([@ANCHOR: rabbitmq_keepalive_loop]). Every `KEEPALIVE_SECONDS` (15) it takes the pool lock and, if the connection has been quiet that long, calls `process_data_events(time_limit=0)` ([@ANCHOR: rabbitmq_keepalive_tick]), which answers the broker's heartbeats and sends ours (pika's timer sends one every 30 s; the broker gives up after two silent intervals). The thread sleeps in `Event.wait` (no polling loop), touches the connection only under the same lock every send takes (BlockingConnection is not thread-safe), never touches a connection another process opened, and ends by itself when the pool has no connection or the connection is found dead (it is dropped quietly and the next publish opens a new one). Before a thread ends it unregisters itself from the per-process thread table, unless a newer thread has already replaced it, so a stale thread can never remove its successor's entry ([@ANCHOR: rabbitmq_forget_keepalive]). A thread does not survive `fork`, so a forked Odoo worker starts its own the first time it opens a connection; fork hooks hold the pool lock across `fork` so the child never inherits it locked ([@ANCHOR: rabbitmq_reset_after_fork]). At interpreter exit an `atexit` hook stops every keepalive thread this process started and closes its pooled connections ([@ANCHOR: rabbitmq_shutdown_all]); per pool class that is the clean shutdown, which sets the thread's stop event, closes the connection this process opened, and joins the thread ([@ANCHOR: rabbitmq_pool_shutdown]).

Why a thread rather than pika's `SelectConnection`: the callers' API (`basic_publish`, `basic_get`, `queue_declare`) is the blocking one, and a second, asynchronous connection class would mean rewriting every caller. The thread uses only `threading` primitives, so it works unchanged in Odoo's prefork workers (a real thread) and in its gevent process (gevent monkey-patching makes it a greenlet and pika's sockets cooperative); hams1 runs both.

**Safety net** ([@ANCHOR: rabbitmq_retire_idle_or_inherited_connection]). Before using the pooled connection, `_get_channel()` closes it cleanly and opens a fresh one when it has neither carried a message nor been serviced by the keepalive for `IDLE_RECYCLE_SECONDS` (300; the keepalive thread died or never ran). It also drops, without closing, a connection that another process opened (the pool's class attributes inherited through `fork`): two processes must not share one socket. The retry-once described above stays as the safety net for a broker restart.

### Credentials & Security
The `_get_channel()` logic ([@ANCHOR: rabbitmq_get_channel]) dynamically relies on the `zero_sudo.security.utils` abstract model to fetch RabbitMQ credentials at runtime instead of hardcoding them in the source; the only connection values written in the source are the fallbacks below. The user, password, port and virtual host come from the Odoo system parameters `rabbitmq.user`, `rabbitmq.pass`, `rabbitmq.port` and `rabbitmq.vhost`, read through `zero_sudo`'s whitelisted `_get_system_param()`. If `rabbitmq.port` is unset the code uses `5672`, and if `rabbitmq.vhost` is unset it uses `/`. The user and password fall back to the environment, as described next. The broker host is not a system parameter: it comes from the `RABBITMQ_HOST` environment variable, default `rabbitmq`. If the connection or channel cannot be opened, the error is logged and `_get_channel()` returns `None`.

Which account it uses ([@ANCHOR: rabbitmq_resolve_credentials]): the `rabbitmq.user`/`rabbitmq.pass` system parameters when both are set, otherwise `RMQ_USER`/`RMQ_PASS` from the Odoo process's environment (`odoo.service` loads `/opt/hams/etc/rabbitmq.env`, the same file the RabbitMQ daemons read). With neither, it logs an error and does not connect. There is no fallback to RabbitMQ's factory `guest` account: production published as `guest` this way until 2026-10-03, which kept that account alive on the production broker.

### Post-Commit Hook Strategy
Odoo's `postcommit` hook is the list of callbacks (`cr.postcommit`) that the database cursor runs only after its transaction has committed. `publish()` registers the actual send there itself, so callers simply call `publish()` inside their normal transaction: the message is sent only if that transaction commits, and never if it rolls back. Callers do not need to register their own `postcommit` callback.
