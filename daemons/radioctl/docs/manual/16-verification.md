# 16. Verifying a description: the self-test, the bench runner and the support list

A rig description is a claim about a radio. Chapter [6](06-rig-descriptions.md) says how a fact records
where it came from and what has been checked; this chapter says how the checking is done and how the
result reaches the published list. Everything here is **implemented**. What it has verified so far is
small: the count is in [`RIG_SUPPORT.md`](../RIG_SUPPORT.md) (<!--count:hardware_verified-->1<!--/count-->
description is `hardware-verified`).

## Where the result is recorded

- The state of each fact is in its `verified` field in `rigs/<id>.toml`: `unverified`, `manual-checked`,
  `transcript-checked` or `hardware-verified`. There is no other copy.
- Who reported a hardware test is in `rigs/reports/verified.toml`, one `[[report]]` per radio and test
  day (`rig`, `radio`, `firmware`, `date`, `reporter`, `issue`, `transmit_tested`). A description with a
  `hardware-verified` fact needs a report there and a report needs such a description; nothing is copied
  between the two.
- [`RIG_SUPPORT.md`](../RIG_SUPPORT.md) is generated by `python3 tools/rig_support_matrix.py` from the Hamlib
  capability matrix (`data/hamlib-4.6.2/`), the descriptions and `verified.toml`. It lists every Hamlib
  model with its tier, family, engine, status (`described`, `engine only`, `needs variant`,
  `needs engine`, `odd device` or `not applicable`, the last with its reason) and the highest verified
  state of its facts. `python3 tools/rig_support_matrix.py --check` and the test beside it fail when the
  file is stale or when the facts and `verified.toml` disagree.
- The numbers that the README and this manual quote from that list are marked in the text, and
  `python3 tools/doc_counts.py --check` (with its test) fails when one drifts; run it without
  `--check` to correct them.

## radioctl-selftest

`radioctl-selftest` is the program a volunteer runs on a radio. It is built from `radioctld`
(`cargo build --release -p radioctld --bin radioctl-selftest`), has every `rigs/*.toml` description
embedded, and is also packaged with the hams.com local relay. `--rigs-dir DIR` or `RADIOCTL_RIGS` use a
directory of descriptions instead. The volunteer instructions are
[`../VOLUNTEER_TESTING.md`](../VOLUNTEER_TESTING.md); what follows is what the code does.

```text
radioctl-selftest [--list] [--version] [--no-discover] [--rigs-dir DIR]
       [--description ID] [--port PATH|usb:VID:PID[:SERIAL]|virtual] [--baud N|auto] [--unmanaged]
       [--update] [--no-update-check] [--out FILE] [--out-dir DIR] [--name NAME] [--email EMAIL]
       [--no-upload] [--server URL]
```

- **Discovery.** With no `--description` and `--port` it looks for radios without writing to anything that
  is not a radio. A port whose own text says it is not a radio (a GPS receiver, an Arduino, a
  programmer) is skipped untouched; a port whose product string names exactly one description is tested
  with it; one that fits several is asked with the descriptions' own read-only identify commands, at the
  rates the baud probe tries, and is `ambiguous` and skipped if the answers do not leave exactly one;
  one with no evidence is `unidentified` and never opened. FlexRadio network radios that announce
  themselves are listed (the discovery broadcast is only listened to). `--list` prints the ports and
  every description.
- **Read-only.** The operations it may send are a fixed list in `selftest.rs` (`is_read_only`): frequency,
  mode, PTT state, signal and power meters, split, transmit VFO, RIT, XIT, filter width, levels, SWR,
  the other meters, model id, firmware and the power-amplifier query. Anything else is refused by the
  tool itself. It never opens the transmit gate and has no PTT, Morse or set command. It runs only the
  checks the description claims, so it needs no code per radio.
- **The VFO knob check.** For a description that claims it reports its own changes (the `transceive`
  capability), and only at a terminal, the last check asks the volunteer to turn the VFO knob and waits
  up to 15 seconds. It sends nothing; it counts only events the radio reported unasked, never the
  answers to its own polls, and never turns the radio's setting on. Without a terminal it is skipped.
- **The report.** One local file per radio (`radioctl-selftest-ID.txt` in `--out-dir` or the current
  folder) and a run summary, with every check's `Pass`, `Fail` or `NotApplicable` and every byte
  exchanged with the radio, in both directions. Exit status: 0 when no check failed, 1 when a check
  failed or a radio could not be opened, 2 for a usage error; a failed upload never changes it.
- **The upload.** At the end of a run it sends one report per radio to `https://hams.com/api/rig-reports`
  without asking (`--no-upload` writes the local report only; `--server URL` is for testing). The
  payload is the JSON in [`../RIG_REPORT_UPLOAD.md`](../RIG_REPORT_UPLOAD.md): the check results and the
  bytes exchanged, the radioctl version, the operating system and processor type, and the name and
  email the volunteer chose to give. No host name, user name, file path or USB serial number is
  sent. The client gives up after 10 seconds, and a failed upload is reported in one line. Treat the
  report as public: the bytes can include a radio's serial number or a callsign set in the radio,
  and there is no expectation of privacy on hams.com.
- **Updating.** At the start of a run it asks the relay's release channel whether a newer version
  exists (5 seconds, then it carries on). It never updates silently: at a terminal it asks, and
  `--update` installs without asking; `--no-update-check` skips the check. A download is accepted only
  if its sha256 matches and its signature verifies against the relay's release key. There is no version
  floor, by the relay's standing rule. A copy built from source has no update channel.

A pass means the read commands worked. It says nothing about PTT or CW, and it does not make a fact
`hardware-verified`; a maintainer does that.

## The bench runner

For the radios the project's maintainers own, `tools/bench_verify.py` walks the checks of
[`../BENCH_VERIFICATION.md`](../BENCH_VERIFICATION.md), the runbook that lists every open hardware check in the order
to do them on one bench day, with the equipment, the rules and the expected results.

```text
bench_verify.py list
bench_verify.py detect
bench_verify.py verify RIG_ID [--port P] [--baud N] [--out-dir D] [--only A5,B2] [--auto-only]
                              [--transmit] [--max-transmit-s N] [--no-upload]
```

It reads the runbook and keeps no second copy of the checks. It detects what is attached (reusing
`radioctl-selftest --list`, which opens no port), runs the checks it can automate (the gate check, the
discovery list, the read-only self-test, reads through `radioctld`, a bounded PTT key and the
watchdog), and for the rest prints the runbook steps and records the operator's answer. **It never
transmits by default:** a transmit check is a dry run unless `--transmit` is given, the operator types
`DUMMY LOAD ATTACHED`, and every safety precondition holds (the earlier checks passed, and the port is not a bare
`ttyUSBn` or `ttyACMn`: only a `/dev/serial/by-id` path, `usb:VID:PID`, a pty or `virtual` names a radio); if one fails the step is
refused and the reason is reported. It writes `BENCH-REPORT-<rig>-<date>.txt` and a
`verified.toml.proposed`, which is a proposal only: it never edits `verified.toml` or a description.
Its self-test step uploads like the self-test does, unless `--no-upload` is given.

## Promoting a description

A maintainer, not the volunteer's tool, raises a fact's state (the procedure is in
[`../VOLUNTEER_TESTING.md`](../VOLUNTEER_TESTING.md)):

1. Read the whole report and confirm the model, the description id and that the radio was in a sane state.
2. For `transcript-checked`: scrub the capture (serial numbers, callsigns), turn it into a transcript
   with `tools/wire_to_transcript.py` (chapter [6](06-rig-descriptions.md)) and cite it in the facts it covers.
3. For `hardware-verified`: set `verified` on each fact the report shows working, with the radio, the
   firmware, the date and exactly what was tested. Mark PTT and CW only if the transmit procedure was
   run and went well.
4. Add the `[[report]]` to `rigs/reports/verified.toml`, fix the description for anything that failed,
   and run `python3 tools/rig_support_matrix.py` to regenerate the list.

The KX3 is the one description that has been through this: its bench run of 2026-11-05 included a keyed
transmission into a dummy load, and `verified.toml` records `transmit_tested = true` for it.
