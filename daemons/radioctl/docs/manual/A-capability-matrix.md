# Appendix A. Capability matrix

Two different tables are summarised here: what Hamlib 4.6.2 says about the 313 radios it lists
(generated by radioctl's Tier 1 tool), and what radioctl's own rig descriptions claim today.

## Hamlib 4.6.2, from `rigctl --dump-caps`

`tools/hamlib_caps_matrix.py` runs `rigctl -l` and `rigctl -m N --dump-caps` for every model and writes
`data/hamlib-4.6.2/capability_matrix.json` (one entry per model, with the parsed report under `dump` and
radioctl's own planning classification under `derived`) and `data/hamlib-4.6.2/HAMLIB_DIFFERENCES.md`
(the generated summary). **Provenance:** the input is program output only. No Hamlib source was read and
no Hamlib table was copied. The `derived` fields (protocol family, VFO model, scope flag, quirk hints)
are radioctl's own rules, recorded with the rule that fired (`family_basis`); they are planning hints, not
statements about a wire protocol.

Regenerate or check for drift:

```sh
nice -n 10 python3 tools/hamlib_caps_matrix.py --out-dir data/hamlib-4.6.2           # regenerate
nice -n 10 python3 tools/hamlib_caps_matrix.py --check --out-dir data/hamlib-4.6.2   # drift check
```

For a new Hamlib release, generate into a new `data/hamlib-<version>/` directory and diff against the old
one. The numbers below are those of `HAMLIB_DIFFERENCES.md` for 4.6.2; the file is the reference.

| Fact | Value |
|---|---|
| Models listed by `rigctl -l` | 313 (the proposal said 314; that count included the header line) |
| Dumped | 312. Model 2 (NET rigctl) fails with `rig does not have tx_range` and is recorded as not dumpable. |
| Backend status | Stable 252, Beta 57, Alpha 3 |
| Port types | RS-232 270, network 15, device driver 10, USB 10, none 3, parallel 2, UDP network 2 |

Derived protocol families (models, of the 312 dumped):

| Family | Models | | Family | Models |
|---|---|---|---|---|
| `other_serial` | 94 | | `kenwood_hh_ascii` | 10 |
| `icom_civ` | 79 (7 with a scope) | | `other_device_driver`, `other_usb` | 10 each |
| `yaesu_legacy` | 31 | | `flexradio_network` | 9 |
| `kenwood_ascii` | 25 | | `other_network` | 8 |
| `yaesu_newcat_ascii` | 15 | | `elecraft_ascii` | 7 |

(The remainder: Icom marine 4, Icom PCR 4, parallel 2, virtual 2, other 2.)

What the Hamlib 4.6.2 matrix says about the families radioctl has not covered yet is a measure of the
work ahead: 79 Icom CI-V models against the four Icom and three Xiegu radios described, 31 legacy Yaesu
models against three, and 9 FlexRadio network models against four.

## radioctl's rig descriptions

Twenty-one files in `rigs/`, at the time of writing (commit `5a636ff9`). A `yes` means the description
lists the capability (and therefore the handle accepts the operation); the engine must also implement it
(chapter [7](07-protocol-engines.md)). Everything is unverified. `transceive` for the Icom and Xiegu
radios means unsolicited frames are decoded if the radio is set to send them; the CI-V engine cannot
switch transceive on. For the FlexRadio files it means the engine subscribes to the radio's status.
The FlexRadio files claim no S-meter, power or SWR because those arrive on streams the engine does not
read. The table is derived from `rigs/*.toml`; run `grep capabilities rigs/*.toml` for the source of truth.
