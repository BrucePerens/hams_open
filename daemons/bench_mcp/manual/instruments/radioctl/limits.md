# radioctl limits and safety model

* Tiers: information tools are `read_only`; changing the rig is `read_config` or higher. The server refuses a tool above the instrument's tier and does not list it.
* Every radioctld command has a timeout (`reply_timeout_s`, default 3 s). Reads are tried twice, over a new connection the second time; commands that change the rig are never repeated blind. A rig that does not answer is an error with a next step; no value from before a failure is reused.
* Arguments sent to radioctld are limited to letters, digits and `_ . + - / :` and 64 characters, so no argument can carry a second command. There is no raw-command tool.
* radioctld listens on 127.0.0.1 only. The config refuses a remote radioctld unless the owner sets `allow_remote_radioctld`; it then has no authentication, and the owner accepts that.
* The managed radioctld is stopped when the server stops. If the server is killed (SIGKILL), the daemon is left running until the next start of the server stops it; the pages on transmitting say what that means for a keyed rig.
* A serial device that is missing, or that this user may not open, is reported before a daemon is started, because radioctld keeps running after it fails to open a rig.
* Receive frequencies must lie inside the rig's reported receive range and the owner's `rx_ranges_hz`; a scan is at most 400 steps and 120 s. The receiver-control tool never sets a transmit-side level or function and refuses to change anything while the rig reports PTT on.
* Starting the daemon opens the serial port. radioctld opens it 8N1 with DTR and RTS inactive and never changes them, and its settings for the lines are not configurable; a rig whose interface keys the transmitter from one of them is outside this safety model, and the owner checks the interface before the first start. `bench_radioctl_diagnose` says so and never opens the port itself.
* The load plausibility check is evidence, not proof. It listens, with the rig in receive, for what a real antenna hears and compares it with a baseline recorded when the owner attested the load. An open or unplugged connection and an antenna on a dead band at low gain also hear nothing; the baseline is valid only for the cabling and settings it was recorded with; hearing no reference station proves nothing, because propagation can fail on all of them; and a station's ticks in the audio, a reading above the baseline, an unsteady reading, an unreadable S-meter or a dead audio input refuse. The owner's attestation in the config gates transmitting; the software cannot know what is connected. The station table is a starting point and is reviewed by the owner: stations go off the air, and a silent one is "not heard", never a failure.
* **Transmitting is possible only for a rig whose config has the owner's `transmit` attestation, at tier `full`, and only into the owner's listed frequency ranges, modes, power cap and time cap.** There is no default frequency list: the owner lists the frequencies they may use for dummy-load tests and answers for their licence terms. Each keyed call also needs `confirm_dummy_load: true` from the person at the bench, a `reason`, and a passing load plausibility check with a baseline. The caps are never above 200 W or 60 s whatever the file says.
* **What the software cannot know:** whether a dummy load is really connected, that it is rated for the power, that nothing else is on the port, or that the owner's ranges are lawful. The attestation is the control; the load check and the SWR probe are evidence. A rig that reports no SWR cannot be probed; the owner may turn the probe off and accepts that.
* **Releasing the rig.** PTT is keyed only through `set_ptt 1` in one function, with the watchdog process armed first. Every path from there ends in `set_ptt 0` and a read-back: success, an error, an abort for a meter, a panic (a guard's drop), the server stopping or being told to stop (SIGTERM, SIGINT, or its input closing: the radioctl release runs before the daemons are stopped). A separate watchdog process holds the other end of a pipe and its own connection to the daemon: when the deadline passes, when the server dies or is killed (the pipe closes), or when the tool aborts, it sends `set_ptt 0` and sets the lowest power setting. The first contact with a rig after a restart sends `set_ptt 0` again and reports a rig that a crash left keyed.
* **What that does not cover:** the watchdog and the server both being killed at once; the computer, the USB link, the rig's interface or radioctld failing in the middle (the rig then keeps the state it had; many rigs have their own transmit time-out, and the owner should enable it); a rig that ignores `set_ptt 0`; a rig whose PTT line is wired or configured so that opening the serial port keys it. The managed radioctld is configured never to answer reads from its cache, so a read-back after a set is a read of the rig. radioctld unkeys a rig when the client that keyed it disconnects, which is one more way a keyed rig is released, and it also unkeys at start and at exit.
* What the driver reports is what radioctld reports from the rig description. A description can declare a function the firmware lacks (the rig then answers "not available"), and a rig's S-meter scale is its maker's choice.
* Not verified: any real rig through radioctl (bench item `bench-mcp-hardware-checks-after-legacy-hardening`). All tests ran against virtual radioctl rigs (a virtual Elecraft KX3 and others) and a scripted fake of radioctld. `verified: virtual radioctl rig only` on these pages means that. radioctld gives a calibrated S-meter (`STRENGTH`, dB relative to S9) for Elecraft rigs only; for other families the tools that need it (scan, load check, receiver test) report the level as unavailable. A first test on a real rig is the owner's to run; read tools first.
