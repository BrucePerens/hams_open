# Cloudflare Edge Orchestration (`cloudflare`)

*Copyright © Bruce Perens K6BP. Licensed under the GNU Affero General Public License v3.0 or later (AGPL-3.0-or-later).*

This module acts as the command center for your Cloudflare CDN (Content Delivery Network, Cloudflare's worldwide edge cache) and Web Application Firewall (WAF). It automates edge caching, security, and IP bans across multiple websites, eliminating the need to manually manage these settings in the Cloudflare dashboard.

## 🌟 What It Does

* **Multi-Website Support:** Seamlessly manage multiple domains/zones from a single Odoo instance. Credentials and settings are isolated per website.
* **DNS & Routing:** Keep a list of DNS records in Odoo (`cloudflare.dns.record`; types A, AAAA, CNAME, TXT, NS). Editing a row changes nothing at Cloudflare until an administrator pushes it: a push shows a plan first, and applies exactly that plan. It creates and updates only the records Odoo has a row for, and deletes nothing except a record whose row is marked **Retire** (see Technical Documentation). Supports multi-tenant Custom Hostname SSL provisioning, allowing tenants to bring their own domains (`CloudflareRoutingDomain`, this module's extension of `edge.routing.domain`): when a domain mapping is created whose name equals a website's domain and that website has an API token and Zone ID, the module asks Cloudflare to create a custom hostname with a domain-validated certificate; with no matching website, provisioning is skipped. The SSL status stored in Odoo is set from Cloudflare's reply at creation and is refreshed only by calling `action_sync_ssl_status()` (administrators and service accounts only); no cron or button calls it. If Cloudflare refuses to delete a hostname, the local mapping is still deleted and a retry record appears under **Pending Hostname Deletes**.
* **Automated Static Caching & Purging:** It tells Cloudflare to cache Odoo's asset bundles (the combined CSS and JS served under `/web/assets`) for a full year, tagged `odoo-static-assets`. Images and downloads served by `/web/image` and `/web/content` are never edge-cached, because they can be private attachments; per-module `/static/` files do not pass through this hook and keep Odoo's own `Cache-Control`. A static-file change detector (`cloudflare.config.manager._trigger_edge_purge_static_assets`) queues an `odoo-static-assets` purge for every website with credentials when a static file is newer than the last recorded change, but no code path currently calls it at server start, so it does not run on boot by itself. The tag can be purged by hand with the Manual Cache Purge wizard.
* **Intelligent Content Invalidation:** Automatically enqueues purges for specific URLs when website pages, blog posts, or products are edited or deleted. A website menu change enqueues a purge of that website's whole cache, since menus appear on every page.
* **Advanced Caching & Rate Limiting:** Record Cloudflare Cache Rules and Rate Limits in Odoo. These are stored in Odoo only: the module has no Cloudflare API call that deploys them, so they have no effect on the edge until configured in Cloudflare itself.
* **WAF Management:** Build and deploy Cloudflare custom firewall rules from the Odoo backend. **Pull** replaces this website's rules in Odoo with the zone's current custom firewall ruleset; **Push** replaces the zone's whole custom firewall ruleset with the rules in Odoo, so a rule that exists only in Cloudflare is removed. No backup is taken on Push (see Configuration Backups).
* **Honeypot IP Banning:** Ban malicious IPs at the network edge. This module contains no honeypot trap itself; it provides `cloudflare.waf.ban_ip()` for honeypot features in other modules to call. Each ban becomes a Cloudflare IP Access Rule on the website's zone and has no expiry: it stays until an administrator lifts it.
* **Zero Trust & Access:** Provision and manage `cloudflared` tunnels directly from Odoo to secure internal resources. Zero Trust Policies can be recorded in Odoo, but like Cache Rules they are stored in Odoo only and are not pushed to Cloudflare.
* **Turnstile Integration:** Backend validator for Cloudflare's invisible Turnstile CAPTCHA. Without a Turnstile Secret configured for the website, every token is rejected.
* **Analytics Dashboard:** Client action dashboard intended for traffic, security, and performance analytics. It is currently a placeholder: it shows fixed sample numbers, not data fetched from Cloudflare.
* **Configuration Backups:** "Pre-Odoo" backups: when the module is installed, each website whose zone already has custom firewall rules gets a read-only snapshot of that ruleset's raw JSON, taken before those rules are imported into Odoo (the zone's state before Odoo took the rules over). Zones without existing rules instead receive the module's default rules. Backups are taken only at install, not before later pushes, and there is no restore action.
* **Zone Settings Control:** Read and adjust security level, development mode, and browser cache TTL per website, applied to Cloudflare immediately.

## 🚀 Odoo 19 & Zero-Trust Ready

This module is fully optimized for Odoo 19 and adheres to a strict Zero-Sudo architecture: it never uses Odoo's `.sudo()`; work that needs more rights than the current user has runs as a dedicated service-account user (`with_user()`), each holding only the rights its job needs. All Cloudflare edge operations are delegated to specific service accounts, ensuring that even in a multi-tenant environment, credentials and operations remain isolated and secure.

## 🛠️ How to Set It Up

1. Ensure the `cloudflare` module is in your Odoo `addons` directory.
2. Configure credentials per website in **Settings > Cloudflare** (the **Cloudflare Edge Orchestration** section):
   * `CF API Token` (Requires `Zone.Cache Purge`, `Zone.Firewall Services`, and `Account.Cloudflare Tunnel` permissions)
   * `CF Zone ID`
   * `CF Account ID` (Required for Zero Trust Tunnels)
   * `Turnstile Secret` (Optional; required for Turnstile verification)

# Technical Documentation

## 1. Overview
Control plane for the CDN edge. Manages Cache-Tags (labels sent in a response's `Cache-Tag` header so Cloudflare can later purge every cached object carrying that label; this module sets `odoo-static-assets` and `odoo-website-<id>`), WAF bans, and Turnstile CAPTCHA verification to offload processing to Cloudflare's edge.

## Secret canary

When the optional `hams_secret_canary` addon is installed, a newly written API token or Turnstile secret on a website is registered with it (only a salted hash is kept), so that its appearance in a response or a log line raises an alarm. A value that is not a single token (shorter than 16 characters, or with spaces) is logged and skipped; saving never fails because of the canary. A secret saved before the canary was installed is registered the next time it is saved.

## 2. API Interfaces
* **DNS & Hostnames:** `cloudflare.dns.record` rows (A, AAAA, CNAME, TXT, NS) are pushed to Cloudflare by `dns_push_plan()` and `dns_push_apply(hash)` (list view, Action, "Push DNS records to Cloudflare"; administrators only). Odoo is the source of truth. `CloudflareRoutingDomain` provisions Custom Hostnames separately; never add one for a name that is already a zone of the account.
  * **Plan first.** The plan is computed from reads only and shows, per row: `create`, `update`, `delete`, `adopt`, `conflict`, `problem`, `drift`, `unchanged`, with the reason. Apply takes the plan's hash and refuses if Cloudflare or the rows changed since. A row that cannot be planned (no token, no zone, Cloudflare unreachable) is reported and does not hold back the others; an unreachable Cloudflare plans nothing, never "create everything".
  * **What it never does.** It never overwrites a record it did not create: a record that already exists with the same content (and proxied flag) is *adopted*, which stores its id in the row and writes nothing at Cloudflare; one with other content is a `conflict`. Pasting that record's id into the row is the deliberate way to take it over. It never touches a record Odoo has no row for. Deleting or archiving a row removes nothing at Cloudflare; the only delete is the **Retire** flag on a row linked to its record by id. An update keeps the record's TTL (a new record gets automatic TTL).
  * **Rows.** `name` is the full lower-case name without a trailing dot; the zone is found from it (the longest suffix that is a zone the token sees). Credentials: the row's website, else the first website with an API token. `manage` off means observe only (rows that existed before 1.7 were switched to it by the migration). NS and TXT rows, and any name an NS row points at (glue), are never proxied.
  * **DNSSEC.** `hams.com` is DNSSEC-signed; a delegated zone (`callbook.hams.com`, `u.hams.com`) that is not signed needs no DS record, and Odoo has no DS type: an NS delegation with no DS is an ordinary insecure delegation.
  * **Capacity and wildcard guard (1.8).** A push that creates more records than it deletes in a zone reads the zone's plan and record count (GET only) and is refused past 90% of the plan's limit (Free 200, or 1,000 for zones created before 2024-09-01; Pro and Business 3,500; Enterprise has an account quota and is not stopped here). If Cloudflare cannot report either number the growing push is refused, not guessed. A member name delegation (an NS row for one label directly under the zone) is also refused while a `*.<zone>` record exists, or is being created in the same push, because the wildcard would answer for names that have no delegation. [@ANCHOR: cloudflare:COMM_dns_capacity_guard]
  * **No member names (1.11, Bruce 2026-11-11).** Nothing for a `<callsign>.hams.com` name may exist at Cloudflare: hams.com's own name servers answer for members. A name below `hams.com` with a callsign-shaped label (one or two letters or digits, a digit, one to four letters: `k6bp`, `www.k6bp`, `k6bp.callbook`) is refused at every place a name could enter or leave: a `cloudflare.dns.record` row and a `cloudflare.tunnel.route` hostname cannot be saved with one [@ANCHOR: cloudflare:COMM_dns_record_no_member_names] [@ANCHOR: cloudflare:COMM_tunnel_route_no_member_names]; the push plan refuses the whole push when any create or update names one, whatever got the row into the table [@ANCHOR: cloudflare:COMM_dns_member_name_problems]; and the API functions that create or change a record, a custom hostname or the tunnel's ingress list send nothing for one [@ANCHOR: cloudflare:COMM_member_name_refusal]. A delete, an archive and an adoption are never refused, so the existing delegations can be retired at the cut-over. A source scan in the tests fails if any other file in the repositories writes to `/dns_records`.
  * **Plan vocabulary and pure planner.** `utils/dns_plan.py` computes a push as plain data with no Odoo and no network. The eight outcomes a row can have are `create`, `update`, `delete`, `adopt`, `unchanged`, `drift`, `conflict` and `problem`; only `create`, `update` and `delete` write to Cloudflare. [@ANCHOR: cloudflare:COMM_dns_plan]
  * **Record-limit arithmetic.** `record_limit()` maps a zone's plan to its record limit (Free 200, or 1,000 for a zone created before 2024-09-01; Pro and Business 3,500; no per-zone limit for Enterprise or an unknown plan). `capacity_problem()` refuses a push that creates more records than it deletes when the projected total passes the 90% hard stop `CAPACITY_HARD_STOP_PERCENT`. `is_member_delegation()` recognises an NS row for one label directly under the zone, which is what a verified member's name looks like. [@ANCHOR: cloudflare:COMM_dns_capacity]
  * **Planning a push.** `dns_push_plan()` reads Cloudflare (GET only) for each selected row and returns the entries, any whole-push problems, a hash of what would be written and a text rendering. It is for administrators only, and a row it cannot plan becomes a `problem` entry instead of stopping the others. [@ANCHOR: cloudflare:COMM_dns_push_plan]
  * **Whole-push refusals.** `_dns_problems()` is the hook that returns reasons the entire push must be refused; the base implementation returns the member-name, capacity and wildcard problems, and other modules can extend it the way tunnel pushes extend `_ingress_problems`. A refused plan is shown as `REFUSED: ...` and cannot be applied. [@ANCHOR: cloudflare:COMM_dns_problems_hook]
  * **Applying a push.** `dns_push_apply(hash)` recomputes the plan and applies it only when it is not refused and its hash equals the one the administrator saw; it creates, updates, adopts or (for a Retire row linked by id) deletes, records the outcome in each row's `cf_last_result`, and returns one result line per row. A failed write is reported on that row and does not stop the others. [@ANCHOR: cloudflare:COMM_dns_push_apply]
  * **Who may push.** `_check_dns_caller_authorized()` raises an access error unless the caller is the superuser or in the Settings administrator group, and both planning and applying call it first. [@ANCHOR: cloudflare:COMM_dns_check_caller_authorized]
  * **Push wizard.** "Push DNS records to Cloudflare" opens `cloudflare.dns.push.wizard` for the selected rows (or all rows when none are selected). Its first step, `action_plan()`, stores the plan text, its hash and the number of things Apply would act on (writes, adoptions and already-gone retirements), prefixing the text with `REFUSED:` when the whole push is refused. [@ANCHOR: cloudflare:COMM_dns_push_wizard_plan] The second step, `action_apply()`, refuses until a plan exists and then applies exactly the plan whose hash it stored, showing the per-row results. [@ANCHOR: cloudflare:COMM_dns_push_wizard_apply]
  * **Row validation.** Saving a `cloudflare.dns.record` checks that the name is a lower-case full name of at least two labels with no trailing dot; that A and AAAA content is an address of that kind, NS and CNAME content is a host name and TXT content is 1 to 2048 characters; that NS and TXT rows are not proxied; that a stored Cloudflare id is 32 lower-case hex characters; and that no other active row has the same type, name and content. [@ANCHOR: cloudflare:COMM_dns_record_constraints]
  * **Nameserver glue stays DNS-only.** A name that an NS row points at cannot be a proxied A or AAAA row, and an NS row cannot point at a name that has a proxied address row, whichever is saved first, because a proxied row would hand resolvers Cloudflare's addresses instead of the nameserver's. [@ANCHOR: cloudflare:COMM_dns_record_glue_unproxied]
  * **Pending pushes.** Cloudflare, "Push pending DNS changes" opens the push wizard with the plan already made for the managed rows not yet at Cloudflare and the rows marked Retire; one more click applies exactly that plan. [@ANCHOR: cloudflare:COMM_dns_push_pending]
  * **Comment.** A row's `comment` (500 characters) is sent to Cloudflare as the record's comment, which the dashboard shows: write one for anything not obvious from the name and value (an `_acme-challenge` CNAME and what it delegates, a DNS-only record and why it cannot be proxied). A different comment makes the plan an UPDATE of the comment alone; an empty comment says nothing and never clears one set at Cloudflare. Scripts that enter rows (`devbox_tools/*_dns_row*.py` in hams_com) set it.
  * **Extension.** `cloudflare.dns.record._dns_problems(entries)` returns strings that refuse the whole push, as `cloudflare.tunnel._ingress_problems` does for tunnels.

* **Traffic Control:** Management of `cloudflare.rate.limit` and `cloudflare.cache.rule` (local records only, not synchronized to Cloudflare).

* **Zero Trust Policies:** Management of `cloudflare.zero.trust.policy` models (local records only, not synchronized to Cloudflare).

* **Configuration Backups:** Management of `cloudflare.config.backup` for pre-Odoo state snapshots (created at install by `initialize_cloudflare_state()`).

* **Zone settings wizard.** "Always Use HTTPS" is sent to Cloudflare for the zone when the administrator picks a value, and left alone when none is picked. The HSTS choice is sent as Cloudflare's `security_header` setting: on carries the max age (86400 seconds when blank), include-subdomains, nosniff and, if asked, preload; off sends a disabled header with a zero max age. The "Respect Existing Headers" box sends Browser Cache TTL 0, so a zone stops overriding the origin's `Cache-Control: no-store` with its own max-age; a plain TTL of 0 is still never sent.

* **Tunnel entry points are gated.** `action_sync_tunnels` is a public model method that any logged-in session, including the public website user, could dispatch; `_check_tunnel_caller_authorized()` refuses it unless the caller is in the Cloudflare Tunnel group, a Settings administrator or a service account, before any Cloudflare call is made. [@ANCHOR: cloudflare:COMM_check_tunnel_caller_authorized]

* **Per-company encryption keys.** Website secrets (the Turnstile secret and the API token) are encrypted with a random per-company key, one `cloudflare.tenant.key` row per company, rather than one key shared by every tenant. The row holds that key wrapped by the deployment-wide crypto secret, and only one row is allowed per company. [@ANCHOR: cloudflare:COMM_tenant_key_fields] `_get_or_create_fernet(company)` returns the company's cipher, creating and wrapping a key on first use (two concurrent first reads end up on the same row), and returns `None` when the deployment secret is missing or malformed or the stored key cannot be unwrapped. [@ANCHOR: cloudflare:COMM_tenant_key_get_or_create_fernet]

* **WAF IP Banning:** `env['cloudflare.waf'].ban_ip(...)` creates a Cloudflare IP Access Rule (block or challenge) for the address on the website's zone and records it in `cloudflare.ip.ban` `[@ANCHOR: cf_execute_ban]`. Supports multiple websites. Callers must be in the Cloudflare WAF group, be Settings administrators, or be service accounts. Repeat calls for an already-active ban do nothing; a ban that could not be sent (no credentials, API error) is recorded with state `failed` and retried on the next call.

* **WAF Management:** Pull and push firewall rules.

* **Cache Purging:** `env['cloudflare.purge.queue'].enqueue_urls(...)` and `enqueue_tags(...)`. Processes an asynchronous queue grouped by website to prevent credential mixing. The "Process Cache Purge Queue" cron runs it every minute as the purge service account, up to 10 batches of 30 entries per run. A successful purge deletes its entries; an "everything" purge also drops that website's other pending entries. Entries for a website with no API token or Zone ID are dropped (they can never be sent) and a pager incident `Cloudflare purge queue` (medium) tells the on-call that the website's purges are not reaching Cloudflare. Entries whose API call fails are marked `failed`, raise the same incident at high severity, and are set back to pending once, an hour later, if the website has credentials. A later batch of that website that succeeds closes the incident. The incident is raised only when `pager_duty` is installed (`_pager_incidents()` returns None otherwise). After saving a token for a website, run Manual Cache Purge with "Everything" for it.
* **Purge incident posts as the pager account:** while the purge queue opens or closes its pager incident, the pager service account is the transaction's default env, because Odoo re-checks `res.partner` read on message recipients as the cron's own account, which must not read contacts.

* **Turnstile API:** `env['cloudflare.turnstile'].verify_token(...)` evaluates tokens against the Cloudflare API.

* **Edge Context:** `env['cloudflare.utils'].get_request_context()` extracts geographic and threat data from trusted headers `[@ANCHOR: cf_get_request_context]`. "Trusted" means the `CF-*` headers are used only when the connecting peer is loopback (the Tunnel case) or inside the trusted Cloudflare IP range allow-list (empty unless an administrator turns on **Trust Cloudflare's Published IP Ranges** in Settings, for a deployment without a Tunnel); from any other peer every geographic and threat field is returned as `None`, so a direct request to the origin cannot forge them.

* **Tunnel Management:** Wizard generates installation commands. Sync and delete tunnels across accounts,.

* **Multi-website tunnels:** one server fronting several websites is the ordinary case here. The "Ensure Tunnel Daemon Running" cron keeps **every** tunnel that has credentials up, one `cloudflared` daemon per tunnel, each tracked under its own Cloudflare tunnel id: a running tunnel is never started twice, a dead one is restarted, and one website's Cloudflare failure never stops another's tunnel. "Routes pushed yet?" lives on the tunnel record (`routes_provisioned`); installs carrying the old single `cloudflare.tunnel.provisioned` system parameter have it folded onto the one tunnel it was really about, once.

## 3. Automated Subsystems
* **Header Injection:** Injects `Cloudflare-CDN-Cache-Control` headers via `ir.http._post_dispatch`. This code, the first-visit cookie rules and the CSRF refresh script live in the `edge_cache` module (a dependency of this one, usable on its own by an instance with no Redis). Dynamic and sensitive routes are excluded.

* **Request Context Safety:** Safely extracts edge headers even in non-HTTP or unbound request contexts `[@ANCHOR: cf_get_request_context]`.
* **Boot-time Sync:** `_trigger_edge_purge_static_assets()` scans installed modules' `static/` folders and queues an `odoo-static-assets` tag purge for every website with credentials when the newest file is newer than the `cloudflare.last_static_mtime` system parameter. Nothing currently calls it at boot (only its test does), so this runs only when invoked explicitly.
* **Content Hooks:** Automatically enqueues purges for `website.page`, `blog.post`, `product.template`, and `website.menu` modifications and deletions. A record with no website is purged on every website, since it is served on all of them.

## 4. Zero-Sudo & Micro-Privilege Architecture
Strictly adheres to Zero-Sudo architecture using dedicated service accounts:
* `cloudflare.user_cloudflare_purge`: Cache purging.
* `cloudflare.user_cloudflare_waf`: WAF and IP banning, the install-time WAF sync, and Turnstile verification.
* `cloudflare.user_cloudflare_tunnel`: Tunnel management, custom hostname provisioning, and pending hostname delete retries.
* `cloudflare.user_cloudflare_trusted_ip`: Daily refresh of the trusted Cloudflare IP ranges.

## 🔐 Security & Multi-Tenancy
The module enforces website-level isolation through the website's company: record rules let a user see purge-queue, WAF-rule, IP-ban, configuration-backup and tunnel records only for websites whose company is among the user's allowed companies (or that have no company). The Cloudflare Edge menu is visible only to Settings administrators. API tokens and Zone IDs are never exposed to the frontend and are handled exclusively by backend service accounts; the API token and Turnstile secret are stored encrypted with a per-company key, and the credential fields are readable only by administrators and the Cloudflare service groups.

## Pure planner interface (`utils/cache_plan.py`, `utils/dns_plan.py`)

Both modules are plain Python with no Odoo and no network: a model reads Cloudflare, passes the rows and what it found, and gets a plan back as data. Neither writes anything. The plan's hash is what the apply step compares, so an apply always writes the plan the administrator reviewed.

### `clean(rule)` [@ANCHOR: cloudflare:COMM_cache_plan_clean]

In `utils/cache_plan.py`. `rule` is one rule dict as Cloudflare returned it in a zone ruleset. It returns a new dict without the keys in `READ_ONLY_FIELDS` (`version`, `last_updated`, `categories`), which Cloudflare returns but rejects on a write, so the rule can be sent back unchanged in a whole-ruleset PUT. The input is not modified, and no key is added or checked. `merge` applies it to every unmanaged rule, and `plan_hash` to every remote rule, so the hash does not change when only a read-only field changes. No errors, no I/O. **Tests:** `TestCachePlanMerge.test_unmanaged_rule_survives_in_place_without_read_only_fields`.

### `_view(rule)` [@ANCHOR: cloudflare:COMM_cache_plan_view]

In `utils/cache_plan.py`. Returns a dict of the five fields that decide what a managed cache rule does, `COMPARED_FIELDS`: `action`, `action_parameters`, `expression`, `description` and `enabled`. A missing key gives None. `merge` compares the view of the remote rule with the view of Odoo's desired rule: equal means `unchanged`, different means `update`. Fields such as `id`, `version` and `last_updated` are left out on purpose, so a rule that only changed its bookkeeping is not rewritten. Pure; no errors. **Tests:** `TestCachePlanMerge.test_existing_managed_rule_is_updated_in_place_by_id_and_unchanged_is_not_a_write`.

### `merge(remote_rules, desired, managed_names)` [@ANCHOR: cloudflare:COMM_cache_plan_merge]

In `utils/cache_plan.py`. Cloudflare keeps one cache-settings ruleset per zone and replaces it whole on a write, so this merges Odoo's rules into the current ones. `remote_rules` is the zone's current rule list (empty when none), `desired` Odoo's active rules in push order (each with `action`, `action_parameters`, `expression`, `description`, `enabled`; a bypass rule has `action_parameters == {"cache": False}`) and `managed_names` every Odoo cache-rule name, active or not. A rule is managed when its description is such a name. It returns `{"rules", "entries", "problems", "hash"}`: rules in the order managed bypass rules, unmanaged rules untouched, managed cache rules; one entry per rule (`create`, `update`, `unchanged`, `delete` for a managed rule whose Odoo row is inactive, `keep`); and problems for duplicate Odoo names, duplicate remote names, or a failed self-check that the unmanaged rules are unchanged. Pure. **Tests:** `TestCachePlanMerge.test_empty_zone_creates_both_bypass_first`, `TestCachePlanMerge.test_unmanaged_rule_survives_in_place_without_read_only_fields`, `TestCachePlanMerge.test_existing_managed_rule_is_updated_in_place_by_id_and_unchanged_is_not_a_write`, `TestCachePlanMerge.test_inactive_managed_rule_is_the_only_thing_ever_deleted`, `TestCachePlanMerge.test_duplicate_names_are_refused`.

### `_summary(rule)` [@ANCHOR: cloudflare:COMM_cache_plan_summary]

In `utils/cache_plan.py`. Describes one rule in a line for the plan text: "bypass cache" when `action_parameters.cache` is false, else "cache, edge <mode> [<n>s], browser <mode>" taken from `edge_ttl` and `browser_ttl` (the mode defaults to "default" for the edge and "zone default" for the browser), followed by " when " and the rule's expression. It is the reason text of `create` and `unchanged` entries, and of both halves of an `update` ("was: ...; now: ..."). Missing keys are tolerated. Pure; no errors. **Tests:** `TestCachePlanMerge.test_empty_zone_creates_both_bypass_first`.

### `plan_hash(merged, remote_rules)` (cache) [@ANCHOR: cloudflare:COMM_cache_plan_hash]

In `utils/cache_plan.py`. Returns the SHA-256 hex digest of the JSON (sorted keys) of two things: the merged rule list that Apply would write, and the remote rules it was computed from with read-only fields removed by `clean`. The apply step recomputes the plan and refuses unless its hash equals the one the administrator was shown, so a change made at Cloudflare or in Odoo in between forces a new review. The digest is not a secret and not a signature. Pure; no errors. **Tests:** `TestCachePlanMerge.test_hash_changes_when_the_zone_changes`.

### `normalize_content(record_type, content)` [@ANCHOR: cloudflare:COMM_dns_plan_normalize_content]

In `utils/dns_plan.py`. Returns the form in which two spellings of one record value compare equal. The value is stripped; for `NS` and `CNAME` the trailing dot is removed and the text lower-cased; for `AAAA` it is parsed with `ipaddress.IPv6Address` and returned compressed (an unparseable value is just lower-cased); for `TXT` one pair of surrounding double quotes, which Cloudflare adds, is removed; `A` and other types are only stripped. None becomes an empty string. This is what lets `plan_row` and `plan_hash` tell a real change from a spelling difference. Pure; no errors. **Tests:** `TestDnsPlan.test_09_spellings_of_one_value_compare_equal`.

### `effective_proxied(record_type, proxied)` [@ANCHOR: cloudflare:COMM_dns_plan_effective_proxied]

In `utils/dns_plan.py`. Returns True only when the row asks for proxying (`proxied` truthy) and its type is one of `PROXIABLE_TYPES` (`A`, `AAAA`, `CNAME`); for `NS`, `TXT` or any other type it is False even if the flag is set, because the Cloudflare API refuses a proxied record of those types. Used by `_entry`, `plan_row` (both sides of every comparison) and the hash, so a stored flag that can have no effect never makes a row look different. Pure; no errors. **Tests:** `TestDnsPlan.test_02_adopting_refuses_when_the_proxied_flag_differs`.

### `_entry(action, row, reason='', **extra)` [@ANCHOR: cloudflare:COMM_dns_plan_entry]

In `utils/dns_plan.py`. ### `plan_row(row, remote)` [@ANCHOR: cloudflare:COMM_dns_plan_row]

In `utils/dns_plan.py`. Plans one Odoo row (`id`, `name`, `type`, `content`, `proxied`, `manage`, `cf_record_id`, `comment`, `retire`) against `remote`, the list of every record Cloudflare holds under that exact name. ### `_plan_retire(row, remote)` [@ANCHOR: cloudflare:COMM_dns_plan_retire]

In `utils/dns_plan.py`. Plans a row marked retire, the only way a push can delete. ### `plan_hash(entries)` (DNS) [@ANCHOR: cloudflare:COMM_dns_plan_hash]

In `utils/dns_plan.py`. In `utils/dns_plan.py`. ### `record_limit(plan_legacy_id, created_on)` [@ANCHOR: cloudflare:COMM_dns_plan_record_limit]

### `capacity_problem(zone_name, limit, current, creates, deletes)` [@ANCHOR: cloudflare:COMM_dns_plan_capacity_problem]

## Cloudflare API helpers (`utils/cloudflare_api.py`)

All helpers build a fixed `https://api.cloudflare.com/client/v4/...` URL (the Turnstile check uses Cloudflare's siteverify address) and send it through `_make_request`, which adds the Bearer token and a timeout and returns the response (a 404 response unchanged), or None after an error that it logged. The shared session retries up to three times: GET, PUT, DELETE and similar on 429 and 5xx, and POST and PATCH only on 429 (a refused rate-limited request, which cannot have been applied), so a lost POST answer is never replayed into a duplicate. Every helper checks its credentials first and makes no request without them. The token is passed in by the caller and never stored here.

### `purge_urls(urls, token, zone_id)` [@ANCHOR: cloudflare:COMM_cf_api_purge_urls]

`urls` is a list of full URLs, `token` the zone's API token and `zone_id` its Zone ID. It POSTs `{"files": [...]}` to the zone's `purge_cache` endpoint in chunks of 30, which is Cloudflare's per-call limit, with a 10 second timeout, and returns True only when every chunk answered 200. A missing token or Zone ID returns False with no request; an empty list returns True with no request. One failed chunk makes the result False but later chunks are still sent, so the purge queue marks the whole batch failed and retries it. It writes at Cloudflare (a purge cannot be undone) and does not raise. **Tests:** `TestCloudflareApiCalls.test_07_purge_urls_sends_chunks_of_thirty`.

### `ban_ip(ip_address, mode, notes, token, zone_id)` [@ANCHOR: cloudflare:COMM_cf_api_ban_ip]

Creates an IP Access Rule on the zone with `POST /zones/<zone_id>/firewall/access_rules/rules` and the body `{"mode", "configuration": {"target": "ip", "value": ip_address}, "notes"}`. `mode` is `block`, `challenge` or `managed_challenge` (what the caller's selection holds) and `notes` is the reason shown in the dashboard. It returns `(True, rule_id)` when Cloudflare answers 200 with a JSON object, `(False, "Missing credentials")` without a request when the token or zone is missing, and `(False, "API Error")` otherwise. The rule has no expiry; `unban_ip` removes it. The caller, `cloudflare.ip.ban._execute_ban`, stores the rule id. **Tests:** `TestCloudflareApiCalls.test_01_ban_and_unban_use_the_access_rules_endpoint`.

### `unban_ip(rule_id, token, zone_id)` [@ANCHOR: cloudflare:COMM_cf_api_unban_ip]

Removes one IP Access Rule with `DELETE /zones/<zone_id>/firewall/access_rules/rules/<rule_id>`, where `rule_id` is the id `ban_ip` returned. It returns `(True, "Success")` on a 200, `(False, "Missing credentials")` without a request when the token or zone is missing, and `(False, "API Error")` for any other answer, a 404 included, so a rule already removed in the dashboard leaves the Odoo ban `active` and the error is shown to the administrator. It changes the live firewall. The rule id is put in the URL unchecked; it comes from the stored ban record. **Tests:** `TestCloudflareApiCalls.test_01_ban_and_unban_use_the_access_rules_endpoint`.

### `verify_turnstile(token, remote_ip, secret)` [@ANCHOR: cloudflare:COMM_cf_api_verify_turnstile]

Asks Cloudflare's Turnstile siteverify endpoint (`https://challenges.cloudflare.com/turnstile/v0/siteverify`, POST form data, 10 second timeout) whether a visitor's CAPTCHA response is valid. `token` is the response from the browser widget, `secret` the website's Turnstile secret, `remote_ip` the visitor's address, sent as `remoteip` only when known. It returns True only when the JSON answer has `success: true`; a missing secret or token, an HTTP error, a network error or a missing `success` key gives False without raising. The secret leaves the process only in that request. **Tests:** `TestCloudflareApiCalls.test_02_verify_turnstile_posts_the_secret_and_the_visitor_address`.

### `get_zone_ruleset(phase, token, zone_id)` [@ANCHOR: cloudflare:COMM_cf_api_get_zone_ruleset]

Reads the zone's entrypoint ruleset for one phase (such as `http_request_firewall_custom`) with `GET /zones/<zone_id>/rulesets/phases/<phase>/entrypoint`. It returns the ruleset dict (its `id` and `rules`), or None when the credentials are missing, Cloudflare has no ruleset for the phase (404), or the call failed. None therefore cannot tell "none exists" from "could not read"; a planner that must tell the two apart uses `get_zone_ruleset_checked`. The WAF pull and push use this one, so a failed read there is treated as "no ruleset". Read only. **Tests:** `TestCloudflareApiCalls.test_03_ruleset_reads_tell_absent_from_unreadable`.

### `get_zone_ruleset_checked(phase, token, zone_id)` [@ANCHOR: cloudflare:COMM_cf_api_get_zone_ruleset_checked]

The same read as `get_zone_ruleset`, but the result says what happened: `("ok", ruleset)` for a 200 with a JSON object, `("absent", None)` for a 404, and `("error", message)` for missing credentials ("Missing credentials."), a failed call ("API Error"), another HTTP status ("HTTP <code>") or an unexpected body ("unexpected response"). The cache-rule planner and push use it, because planning as though an unreadable zone were empty would replace the real ruleset (the whole ruleset is replaced on a write). Read only; does not raise. **Tests:** `TestCloudflareApiCalls.test_03_ruleset_reads_tell_absent_from_unreadable`.

### `update_zone_ruleset(ruleset_id, payload, token, zone_id)` [@ANCHOR: cloudflare:COMM_cf_api_update_zone_ruleset]

Replaces an existing ruleset with `PUT /zones/<zone_id>/rulesets/<ruleset_id>`. `ruleset_id` is the id read from the existing ruleset, `payload` the whole new ruleset (name, kind, phase and the complete rule list); anything not in `payload` is removed at Cloudflare. It returns `(True, "Ruleset updated successfully.")` on a 200, `(False, "Missing credentials.")` without a request when the token or zone is missing, and `(False, "API Error")` otherwise. The ruleset id is not validated. It changes live firewall or cache behaviour; the callers are the WAF push and the reviewed cache-rule push in `models/config_manager.py`. **Tests:** `TestCloudflareApiCalls.test_04_ruleset_writes_put_to_the_ruleset_and_post_to_the_zone`.

### `create_zone_ruleset(payload, token, zone_id)` [@ANCHOR: cloudflare:COMM_cf_api_create_zone_ruleset]

Creates a new zone ruleset with `POST /zones/<zone_id>/rulesets`; `payload` has the name, kind `zone`, the phase and the rules. It returns `(True, "Ruleset created successfully.")` on a 200, `(False, "Missing credentials.")` without a request when the token or zone is missing, and `(False, "API Error")` otherwise. The WAF push and the cache-rule push call it when no ruleset exists for the phase yet. A POST is retried only after a 429, never after a server error. It changes live behaviour of the zone. **Tests:** `TestCloudflareApiCalls.test_04_ruleset_writes_put_to_the_ruleset_and_post_to_the_zone`.

### `create_cfd_tunnel(account_id, token, tunnel_name)` [@ANCHOR: cloudflare:COMM_cf_api_create_cfd_tunnel]

Creates a Cloudflare Tunnel in the account with `POST /accounts/<account_id>/cfd_tunnel`, sending `tunnel_name` and a fresh `tunnel_secret` (32 random bytes from `secrets.token_bytes`, base64 encoded, never stored or returned). ### Zone settings: Always Use HTTPS [@ANCHOR: cloudflare:COMM_zone_settings_always_use_https]

Part of `CloudflareZoneSettingsWizard.action_apply_settings()` in `models/zone_settings_wizard.py` (a `@public_rpc` wizard method). ### Zone settings: HSTS security header [@ANCHOR: cloudflare:COMM_zone_settings_security_header]

Part of `action_apply_settings()`. When `hsts_status` is set, one Cloudflare setting, `security_header`, is sent as `{"strict_transport_security": {...}}`. With `on` the object carries `enabled` true, `max_age` (`hsts_max_age`, 86400 when blank or zero), `include_subdomains`, `nosniff` and, only when `hsts_preload` is ticked, `preload: true`. With `off` it carries `enabled` false, `max_age` 0, and false for include-subdomains and nosniff, which switches the header off. With `hsts_status` empty nothing is sent. A failed call is collected as "Security Header (HSTS): message" and reported with the other failures at the end. Preload is a commitment that is hard to undo, so it is never sent unless asked for. See also `test_06_apply_sends_hsts_security_header` in `tests/test_zone_settings_always_https.py`.

### Zone settings: Respect Existing Headers [@ANCHOR: cloudflare:COMM_zone_settings_browser_cache_respect_headers]

Part of `action_apply_settings()`. The wizard sends the `browser_cache_ttl` setting when the "Respect Existing Headers" box (`browser_cache_respect_headers`) is ticked or the TTL field is non-zero. With the box ticked it sends 0, which tells Cloudflare to respect the origin's own `Cache-Control` (so an origin `no-store` is not overridden by a zone max-age); otherwise it sends the typed TTL in seconds. A TTL of 0 typed without the box is deliberately never sent: Odoo's Integer field cannot tell "unset" from 0, so an untouched wizard would otherwise wipe a configured TTL. Errors are collected as "Browser Cache TTL: message" and raised together at the end. See also `test_10_respect_existing_headers_sends_zero` in `tests/test_zone_settings_always_https.py`.

### Push WAF rules to Cloudflare [@ANCHOR: cf_action_push_waf_rules]

`CloudflareConfigManager.action_push_waf_rules(website_id=None)` in `models/config_manager.py` is a private model method that publishes the website's `cloudflare.waf.rule` rows (up to 1000, in sequence order) as the zone's `http_request_firewall_custom` ruleset, named "Odoo WAF Rules - <website>". See also `test_04_cf_action_push_waf_rules` in `tests/test_waf_management.py`.

### Purge queue processing [@ANCHOR: cf_process_queue_logic]

`CloudflarePurgeQueue.process_queue()` in `models/purge_queue.py` is the private method the "Process Cache Purge Queue" cron calls every minute. It switches to the `cloudflare.user_cloudflare_purge` service user, calls `requeue_failed()`, then runs at most 10 batches of up to 30 pending rows. Each batch is the rows of the first website in the search (ordered by website and id), so two websites' credentials are never mixed. With no token or Zone ID the batch is deleted, logged, and reported at medium severity. Otherwise an `everything` row purges the zone and also deletes the website's other pending rows that existed before the call; then URL rows and tag rows are sent with `purge_urls` and `purge_tags`. A successful call deletes its rows; a failed one marks them `failed`. It commits after every batch, sleeps 0.1 seconds, and re-triggers its cron if all 10 batches were used. See also `test_01_bdd_queue_batching_and_rate_limiting` in `tests/test_purge_queue.py` and `test_purge_queued_during_the_wipe_is_kept` in `tests/test_purge_everything.py`.

### Opening the purge pager incident [@ANCHOR: cloudflare:COMM_report_purge_failure]

`_report_purge_failure(website, description, severity)` in `models/purge_queue.py` opens (or adds an occurrence to) the pager incident that says a website's purges are not reaching Cloudflare. `website` is the record, `description` the reason and `severity` is `medium` (no credentials) or `high` (API call failed). The incident source is the constant `PURGE_INCIDENT_SOURCE`, "Cloudflare purge queue", and the text names the website and its id. It returns what `report_incident` returns, or False when `pager_duty` is not installed. The call runs inside `_pager_default_env`. Called by `process_queue` once per failed batch. See also `test_01_no_credentials_drops_rows_and_pages_medium` and `test_02_api_failure_keeps_rows_failed_and_pages_high` in `tests/test_purge_queue.py`.

### Retrying failed purges [@ANCHOR: cloudflare:COMM_requeue_failed_purges]

`requeue_failed()` in `models/purge_queue.py` (private, called at the start of every `process_queue` run) makes one more attempt at purges that failed on an API error. It looks at up to 1000 rows in state `failed` whose `write_date` is at least `RETRY_FAILED_AFTER_HOURS` (1) old, keeps only those of websites that now have both an API token and a Zone ID, and sets them back to `pending`. It returns the number of rows set back. A row that fails again goes back to `failed` with a new write date, so the retry repeats hourly while the pager incident stays open. Rows of a website without credentials are left alone (credential failures are deleted, not marked failed). See also `test_04_failed_rows_are_retried_once_an_hour_later_with_credentials` and `test_05_failed_rows_without_credentials_are_not_retried` in `tests/test_purge_queue.py`.

### Closing the purge pager incident [@ANCHOR: cloudflare:COMM_resolve_purge_failure]

`_resolve_purge_failure(website)` in `models/purge_queue.py` closes the purge incident for one website after a batch of its purges succeeded. It calls the pager model's `auto_resolve_incidents(PURGE_INCIDENT_SOURCE, website_id=website.id)` inside `_pager_default_env` and returns its result, or False when `pager_duty` is not installed. `process_queue` calls it after every successful batch of a website that has a record, so a later success closes an incident an earlier failure opened. It never raises for the absence of the pager module. See also `test_03_success_resolves_the_incident` and `test_01_resolve_posts_the_note_when_the_purge_account_is_the_default_env` in `tests/test_purge_queue.py`.

### Pager model access [@ANCHOR: cloudflare:COMM_purge_pager_incidents]

`_pager_incidents()` in `models/purge_queue.py` returns the `pager.incident` model as the `pager_duty.user_pager_service_internal` service user, or None when `"pager.incident" not in self.env`, which is the case for a tenant instance that runs this module without `pager_duty`. In that case the failure is only logged and `_report_purge_failure` and `_resolve_purge_failure` return False. No arguments, no side effects, no database access beyond resolving the service user. See also `test_06_pager_incidents_is_none_without_pager_duty` in `tests/test_purge_queue.py`.

### Pager default environment [@ANCHOR: cloudflare:COMM_purge_pager_default_env]

`_pager_default_env(incidents)` is a static context manager in `models/purge_queue.py`. While active it sets the transaction's `default_env` to the pager service environment (`incidents.env`) and restores the previous one afterwards, even when an exception is raised. Odoo 19 re-checks read access to `res.partner` for the recipients of a message as the transaction's default environment, ignoring the `with_user()` the pager code uses; the cron's purge account must not read contacts, so without this posting an incident note raised an access error. It changes transaction state only for the duration of the `with` block and never raises by itself. See also `test_01_resolve_posts_the_note_when_the_purge_account_is_the_default_env` in `tests/test_purge_queue.py`.

### Turnstile token verification [@ANCHOR: cf_turnstile_verify]

`CloudflareTurnstile.verify_token(token, remote_ip=None, website_id=None)` in `models/turnstile.py` (private, so not reachable over RPC) tells whether a Turnstile CAPTCHA response is valid. `token` is the response from the visitor's browser, `remote_ip` the visitor address (sent to Cloudflare when known) and `website_id` the website whose secret is used (the current website when None). It reads `cloudflare_turnstile_secret` as the `cloudflare.user_cloudflare_waf` service user, because an anonymous visitor's request is the normal caller and may not read that field; this is safe because only a boolean ever leaves. It returns False without a request when no secret is stored, else `verify_turnstile(...)`: True only when Cloudflare answers `success: true`; a failed request is False. See also `test_02_turnstile_secret_fetch` and `test_02b_verify_token_works_for_an_unprivileged_caller` in `tests/test_cloudflare_apis.py`.

### Tunnel setup command [@ANCHOR: cf_tunnel_setup]

`action_generate_tunnel_command()` in `models/res_config_settings.py` (a `@public_rpc` settings action) creates a Cloudflare tunnel and opens a wizard showing the command that installs it. It uses the settings' website (else the current one) and raises `UserError` if its API token or Account ID is missing. It calls `create_cfd_tunnel` with the name `odoo-edge-tunnel-<unix time>`, then `get_cfd_tunnel_token`, and builds `cloudflared service install <token>`; a failure of either call is raised with Cloudflare's message. The command holds a one-time secret, so it is passed only in the action's context to the transient `cloudflare.tunnel.wizard` and is never stored. Side effect: a real tunnel is created at Cloudflare; the Odoo record appears at the next sync. See also `test_03_tunnel_setup` in `tests/test_cloudflare_apis.py`.

### Sync tunnels [@ANCHOR: cf_sync_tunnels]

`CloudflareTunnel.action_sync_tunnels()` in `models/tunnel.py` (a `@public_rpc` model method, called by a button or cron) first runs `_check_tunnel_caller_authorized()`, then calls `_sync_tunnels_for_website` for up to 1000 websites. Each website runs in its own database savepoint inside a try block, so one website's Cloudflare error or constraint violation is logged and the others still sync. `_sync_tunnels_for_website` works as the `cloudflare.user_cloudflare_tunnel` service user: it skips a website with no token or Account ID, lists the account's tunnels and creates or updates one `cloudflare.tunnel` row per tunnel (id, name, status, creation time). Tunnels missing at Cloudflare are not deleted locally. It returns a "Tunnels sync" success notification. See also `test_04_sync_tunnels` and `test_04a_sync_tunnels_isolates_one_websites_failure_from_the_rest` in `tests/test_cloudflare_apis.py`.

### Delete tunnels [@ANCHOR: cf_delete_tunnel]

`CloudflareTunnel.action_delete_tunnel()` in `models/tunnel.py` (`@public_rpc`, operates on the selected records) deletes each tunnel at Cloudflare with `delete_cfd_tunnel(account_id, token, cf_tunnel_id)`. On success it stops that tunnel's `cloudflared` systemd unit with `stop_tunnel_daemon` (so no orphan keeps running) and deletes the local record. A tunnel whose website lacks a token or Account ID, or whose Cloudflare delete fails, is collected as a failure and left in place. If every tunnel failed it raises `UserError` with all messages. With a mix it returns a sticky warning notification rather than raising, because raising would roll back the local deletes already made in the same request. With no failures it returns nothing. See also `test_05_delete_tunnel` in `tests/test_cloudflare_apis.py`.

### Keep every tunnel running [@ANCHOR: ensure_tunnel_running]

`CloudflareTunnel.action_ensure_tunnel_running()` in `models/tunnel.py` (private, run by the "Ensure Tunnel Daemon Running" cron) makes sure every `cloudflare.tunnel` record has its `cloudflared` daemon running. It searches the tunnel records first (up to 10000), which is also the access check, and returns an all-zero summary at once if there are none. Otherwise it runs `_migrate_global_provisioned_flag()` and then `_ensure_one_tunnel_running` for each tunnel inside its own savepoint, so an exception is logged and counted as `failed` without stopping the rest. It returns and logs a dict with the counts `started`, `already_running`, `skipped` and `failed`. See also `test_01_every_website_s_tunnel_is_started_not_just_the_first`, `test_02_a_tunnel_already_running_is_not_restarted` and `test_09_no_tunnels_at_all_is_a_clean_no_op` in `tests/test_tunnel_multi_website.py`.

### Bring one tunnel up [@ANCHOR: ensure_one_tunnel_running]

`CloudflareTunnel._ensure_one_tunnel_running(tunnel)` in `models/tunnel.py` brings one tunnel up and returns one word: `skipped`, `already_running`, `started` or `failed`. It returns `skipped` for a tunnel with no Cloudflare id or whose website has no token or Account ID, and `already_running` when `routes_provisioned` is set and `is_tunnel_daemon_running(id)` is true (no API call is made then). Otherwise it fetches the run token with `get_cfd_tunnel_token`; an error or empty token is logged (the token itself never is) and gives `failed`. If routes were not yet pushed it calls `action_push_configuration()` and sets `routes_provisioned`; a failure there is logged and does not stop the daemon. Then `start_tunnel_daemon(token, tunnel_key=id)` starts it. See also `test_03_one_failing_tunnel_does_not_stop_the_others`, `test_04_the_provisioned_marker_is_per_tunnel` and `test_08_a_tunnel_whose_website_has_no_credentials_is_skipped` in `tests/test_tunnel_multi_website.py`.

### Fold the old provisioned flag [@ANCHOR: migrate_global_provisioned_flag]

`CloudflareTunnel._migrate_global_provisioned_flag()` in `models/tunnel.py` moves the old system-wide `cloudflare.tunnel.provisioned` parameter onto the per-tunnel field `routes_provisioned`. It reads the parameter with `redis_bypass_cache` (the cached read would otherwise keep returning the old value and the migration would repeat every cron tick). If the value is empty or already the "migrated" sentinel it returns False and does nothing. Otherwise it sets `routes_provisioned` on the lowest-id tunnel (the record the old single-tunnel code worked on), not on every tunnel, writes the sentinel into the parameter (kept, not deleted, so a rollback does not re-provision), and returns True. It is called by `action_ensure_tunnel_running` on every run and is safe to repeat. See also `test_05_legacy_global_flag_migrates_onto_the_lowest_id_tunnel`, `test_06_the_migration_runs_once_and_is_a_no_op_afterwards` and `test_07_an_install_that_never_had_the_flag_migrates_nothing` in `tests/test_tunnel_multi_website.py`.

### Edge cache header injection [@ANCHOR: edge_cache:COMM_ir_http_post_dispatch_headers]

`IrHttp._post_dispatch(response)` in `edge_cache/models/ir_http.py` runs after every dispatched response and only ever adds caching directives; it never rejects a request. After the framework's own handling it removes the internal `X-Cloudflare-Edge-Cacheable` opt-in marker (it must never reach the client), marks every 4xx/5xx response `Cache-Control: no-store`, and then sets `Cloudflare-CDN-Cache-Control`: `/web/assets` answers with status 200 or 304 and no cookie get `max-age=31536000` and the `odoo-static-assets` Cache-Tag; the dynamic routes of the next entry get `no-cache, no-store`; a public page gets `max-age=86400` only when it opted in and `_cloudflare_edge_cacheable` accepts it (GET or HEAD, status 200 or 304, public user, no stateful cookie, no Set-Cookie), else `no-cache, no-store`. A cacheable response also gets the tag `odoo-website-<id>` when the request has a website. Returns the framework's result. See also tests `test_01_static_asset_caching`, `test_02_dynamic_route_no_store` and `test_04_website_cache_tag_localproxy` in `edge_cache/tests/test_edge_cache_headers.py`.

### Dynamic routes never cached [@ANCHOR: edge_cache:cf_nocache_routes]

The route classifier inside `IrHttp._post_dispatch` in `edge_cache/models/ir_http.py` marks a response `Cloudflare-CDN-Cache-Control: no-cache, no-store` when the request path starts with `/my/`, `/odoo`, `/web/`, `/api/`, `/shop/cart`, `/shop/checkout`, `/shop/confirm_order` or `/helpdesk/`, and returns at once, whatever the response or opt-in marker says. `/web/` is included on purpose, so `/web/image` and `/web/content` (attachments that depend on the user's access rights) can never be stored and replayed to other visitors; only `/web/assets` is handled earlier and may be cached. The list is a source constant; there is no setting. See also `test_02_dynamic_route_no_store` in `edge_cache/tests/test_edge_cache_headers.py` and `test_login_page_and_post_targets_are_never_cacheable` in `edge_cache/tests/test_edge_cache_cookies.py`.
