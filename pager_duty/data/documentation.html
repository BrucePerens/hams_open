Overview

The Pager Duty module is your central hub for infrastructure health and Site Reliability Engineering (SRE). It provides proactive monitoring, intelligent alerting, and automated incident management.

Getting Started (For Users)

1. Managing On-Call Schedules

Alerts are routed based on the Odoo Calendar. To define who is on call:

  • Create a standard Calendar event for the relevant engineer.
  • Check the "Is Pager Duty Shift" box on the event.
  • The system will automatically identify the active shift and route incident notifications to that specific user. The user paged is the event's own user (its user_id), not its attendees.
  • If shifts overlap, the most recently created shift wins, so adding a new shift overrides an existing one.
  • If no shift covers the current time, no on-call notification is sent; the incident still gets its Helpdesk ticket (if its severity qualifies) and is still escalated.

2. NOC Dashboard

Access the NOC (Network Operations Center) Dashboard via Pager Duty > NOC Dashboard for a real-time, high-visibility overview of your system health.

  • Live Updates: The board refreshes instantly as incidents are created, acknowledged, or resolved. The Pause Updates button stops this until you press Resume Updates.
  • Burn-In Protection: Designed for long-term display on office monitors, the dashboard subtly shifts its layout every 60 seconds to protect your hardware.

3. Acknowledgement & Escalation

  • Acknowledge: When you start working on an issue, click "Acknowledge" on the incident in the NOC Dashboard (the button appears on Open incidents). This signals to the team that the issue is being handled and stops the automatic escalation timer.
  • Paging by severity: A new High or Critical incident notifies the on-call user at once (when the pager_duty.helpdesk_model system parameter is set, the Helpdesk ticket is the notification instead). Low and Medium incidents are recorded without paging; if the same source reports 5 times within 60 minutes, a separate High incident named "Trend: <source>" is raised, and that one pages.
  • Escalation: If an incident of any severity remains unacknowledged (still Open) for more than 15 minutes, the system automatically escalates it by notifying the members of the Pager Duty Admin group for that incident's website (or global admins). The escalation job runs every 5 minutes, and each incident is escalated once.
  • Helpdesk Integration: A tracked Helpdesk ticket, assigned to the on-call responder, is created automatically for every new High or Critical incident and for every incident created from inbound email. There is no button for creating one by hand.
  • Auto-Resolution: When a failing check passes three times in a row, the monitor daemon resolves that check's Open and Acknowledged incidents.

Administrator Guide (For Admins)

1. Configuring Monitoring Checks

To begin monitoring your infrastructure, navigate to Pager Duty > Monitoring Checks. Here, you can define various types of health checks:

  • Web Resources: Monitor HTTP/HTTPS/HTTP3 endpoints.
  • Database Health: Deep health checks on PostgreSQL and MySQL/MariaDB.
  • System Metrics & Network Services: Monitor CPU, RAM, Disk space, and ports.
  • Hardware Monitoring: SMART (Self-Monitoring, Analysis and Reporting Technology) hard drive monitoring.

2. Autodiscovery

Admins can use the "Auto-Discover Services" button in the Monitoring Checks list view. This action automatically scans your server and generates recommended checks for you: memory, CPU, load, failed systemd services, IPv4/IPv6 root DNS reachability, disk space for each mounted ext4, xfs, btrfs, zfs or vfat partition, the PostgreSQL, Redis, RabbitMQ, Nginx and Docker services it finds running, and an HTTP ping of Odoo itself. Checks whose name already exists are skipped, and the daemon configuration file is written afterwards.

3. Manual Triggering

The check form has a "Run Check Now" button, but it does not run the check: the monitoring daemon runs outside Odoo on its own schedule, and the button only displays a notice saying so. A new or changed check runs once its configuration has been pushed to the daemon and the daemon has been restarted (see the next section).

4. Synchronizing with Daemons

After configuring checks in Odoo, you must sync them to the external Python daemons:

  1. Go to the Monitoring Checks list view.
  2. Click Push to Daemon (JSON) (or Pull from Daemon (JSON) to pull changes).
  3. This updates the daemon configuration file (pager_config.json).
  4. Restart the daemon services. They read pager_config.json only when they start.

Push writes every active check. Pull deletes every check in the database and re-creates the checks from the file, so any check not in the file is lost. The file is written to the directory named by the pager_duty.config_dir system parameter (default /opt/hams/etc) when that directory is writable, and otherwise to the module's daemon/ directory.

5. Multi-Website Awareness & Security

Pager Duty can isolate checks, incidents, and schedules by website. Data is secured via micro-privileges and a pager_service_internal zero-sudo account.

6. Log Analyzer (Splunk-style)

The integrated Log Analyzer tails system logs in real-time. Define regex patterns to watch for critical errors. The Interactive Log Search tool allows Admins to perform live regex searches across server log files directly from the Odoo UI. Only files under /var/log that are registered under Log Analyzer > Target Files (and visible to you) can be searched.

7. Synthetic Journeys & Sandboxing

Admins can write Playwright (Python) or Bash scripts to simulate user behavior. These are executed in a Bubblewrap (bwrap) sandbox. With the default Loop-back network only setting the sandbox has no access to the host's network; choosing Full network access lets the script reach the internet and LAN. The separate "Synthetic Journey (Script)" check type is not sandboxed: it runs its command directly in the monitoring daemon.
