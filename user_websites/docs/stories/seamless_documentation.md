## XPath Rendering Technical Elements
The platform dynamically injects content using XPath. The following elements have been verified. Each entry says which template it extends, what it adds and which test covers it (ADR 0113). The tests are the methods of `tests/test_xpath_rendering.py`, whose anchors are `test_xpath_rendering_appeal`, `test_xpath_rendering_portal_docs` and `test_xpath_rendering_navbar_head`.

### Appeal alert on the portal home [@ANCHOR: user_websites:xpath_rendering_appeal]

In `views/user_websites_templates.xml`, the template `portal_my_home_appeal` inherits `portal.portal_my_home` with an XPath on the `o_portal_my_home` div (position `before`) and adds, above the portal's own content, the templates dropzone, then a red "Account Suspended" alert when the signed-in user `is_suspended_from_websites` and one alert per group in `suspended_group_ids`. Each alert either says "We are currently reviewing your appeal" when an appeal in state `new` exists, or shows the one-time appeal form that posts `reason` (and a hidden `group_id` for groups) with a CSRF (cross-site request forgery) token to `/website/submit_appeal`. It reads the user's `appeal_ids`; it writes nothing itself. A user who is not suspended sees none of it. Test: `tests/test_xpath_rendering.py::test_05_portal_templates` loads `/my/home` as a portal user and checks the page renders with the dropzone in place; the suspension appeal form is exercised by the tour `moderation_appeal_tour.js`.

### Privacy and Data card in the portal documents list [@ANCHOR: user_websites:xpath_rendering_portal_docs]

In the same template file, a second XPath of the template `portal_my_home_appeal` targets the div with class `o_portal_docs` of `portal.portal_my_home` (position `inside`) and calls the portal's `portal_docs_entry` card with the title "Privacy & Data", the text "Manage your data, export content, and right to erasure.", the link `/my/privacy` and `config_card` true, so every signed-in portal user gets a tile that leads to the privacy dashboard (see the privacy story). It takes no arguments of its own and renders for everyone who may see `/my/home`. Test: `tests/test_xpath_rendering.py::test_05_portal_templates`, which logs in as a portal user, loads `/my/home` and checks that "Privacy" and "Data" are in the response.

### Navbar context in the page head [@ANCHOR: user_websites:xpath_rendering_navbar_head]

In `views/user_websites_templates.xml`, the template `layout_inherit_user_navbar` inherits `website.layout` with an XPath on `//head` (position `inside`). It runs for every website page and only sets QWeb variables, so other templates can read them: `profile_user` (the profile owner, taken from the main object through the mixin method `_user_websites_navbar_profile_user()` rather than by reading `owner_user_id` directly, because that read would be a 403 for the public user and for other members), `profile_group`, `resolved_slug` (the owner's or group's slug), `page_type` ("blog" when the path contains "blog", else "home"), `is_owner` (the viewer is the profile user or a member of the group), and `member_site` (true for the site's own pages and owner tools), which turns off the stock header and footer in favour of the member's own, plus a `user_websites_slug` meta tag. Values already supplied by a controller are kept. No writes. Tests: `tests/test_xpath_rendering.py::test_07_navbar_rendering` checks the meta tag and the navbar, and `test_07b_navbar_member_owned_record_public_visitor` checks a member-owned record renders for a logged-out visitor and for another member.
