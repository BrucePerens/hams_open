# `user_websites/static/src/js/toast_notifications.js`

Two page scripts tell people what happened: a visitor after a form, and a site administrator about reports waiting for review. Tests: `static/tests/toast_notifications.test.js` (hoot unit tests, with fetch mocked) and, for the real address handling in a browser, the tour `test_tour_toast_notifications` run from `tests/test_ui_tours.py`. Both classes are registered in `registry.category("public.interactions")` with the selector `#wrapwrap`, so they start on every website page. Both use Odoo's own notification service (`this.env.services.notification.add`), not custom markup, so the toasts look like any other Odoo toast and need no template.

### `UrlToastNotification.start()` [@ANCHOR: user_websites:js_toast_notifications_url_start]

Lifecycle method called by the public-interaction framework once the page is ready. It takes no arguments, returns nothing and only calls `_checkUrlForNotifications()`, so that the address is examined exactly once per page load, never on a later re-render. It has no side effects of its own and cannot fail except through what the called method does. Test: `both toasts check on start` in `static/tests/toast_notifications.test.js`, which calls each class's `start` with a stand-in `this` whose checking method records the call and verifies each is called once.

### `UrlToastNotification._checkUrlForNotifications()` [@ANCHOR: user_websites:js_toast_notifications_check_url]

Reads the page's query string and shows one non-sticky toast for the first matching parameter, in this order. `report_error=<reason>` shows a red "Report not sent" toast with the words for that reason from the exported table `REPORT_ERRORS` (`missing_fields`, `short_description`, `gibberish`, `too_many_urls`, `bad_email`, `foreign_target`, `expired`, `ip_changed`, `too_fast`, `wrong_answer`, `creation_failed`; any other reason shows the `default` words; reasons that identify a program are never sent by the server, so a program learns nothing). Then `report_submitted` ("Success", "We received your report and will review it."), `appeal_submitted` ("Submitted"), `subscribed` ("Subscribed", weekly digests) and `erased` ("Content Deleted"). When something was shown it rewrites the address with `history.replaceState` to the same path without a query string, so a reload does not repeat the toast and the back-button history is not changed. No parameters means nothing happens. Pure client side. Tests: three tests in `static/tests/toast_notifications.test.js` (each success parameter and the cleaned address, a refused report with the default words for an unknown reason, a page without the parameters).

### `AdminViolationToast.start()` [@ANCHOR: user_websites:js_toast_notifications_admin_start]

Lifecycle method of the moderation toast class. No arguments; it calls `void this._checkPendingReports()` and deliberately ignores the returned promise, so the page never waits for the request. Because the interaction runs for every visitor, not only moderators, the permission decision is made by the server endpoint (a non-moderator is told the count is 0 and nothing shows), not here. Returns nothing. Test: `both toasts check on start` in `static/tests/toast_notifications.test.js`.

### `AdminViolationToast._checkPendingReports()` [@ANCHOR: user_websites:js_toast_notifications_check_pending_reports]

Fetches `/api/v1/user_websites/pending_reports` and returns the promise. A non-OK response is treated as an error; any error is swallowed so a network failure never breaks the page. With the JSON answer it asks `shouldShowToast(readSeen(), data, Date.now())`; if the answer is yes it shows a sticky warning titled "Pending Moderation" with the text "There are N pending violation reports requiring review.", a primary "Review reports" button that sends the browser to `data.url` (only when it is a string starting with `/`, so a hostile value cannot send the administrator off the site) and a "Dismiss" button, then records the sighting with `writeSeen(data, now)`. Resolves with `null` in every case. Tests in `static/tests/toast_notifications.test.js`: a toast is shown for a pending count, silence for a count of zero, a network failure is swallowed, the same queue is not shown twice but a grown one is; the tour `test_tour_toast_notifications` covers it in a real browser.

### `readSeen(storage)` [@ANCHOR: user_websites:js_toast_notifications_read_seen]

Exported helper. `storage` (optional object with `getItem`, default `window.localStorage`; the parameter exists for tests). It reads the key `admin_violation_toast_seen` and returns the parsed object `{count, latest_id, ts}` (the queue size and newest report id shown last, and the time in milliseconds since the epoch), or `null` when nothing is stored, the stored text is not valid JSON or the storage throws (a private window or blocked site data). Never throws; it does not write or validate field types (`shouldShowToast` does that). The value lives only in this browser, so each device shows the toast once per period. Test: `readSeen returns what was stored, null when nothing is stored, and null when the storage refuses` in `static/tests/toast_notifications.test.js`.

### `writeSeen(data, now, storage)` [@ANCHOR: user_websites:js_toast_notifications_write_seen]

Exported helper. `data` is the endpoint's answer (`count`, optional `latest_id`), `now` the current time in milliseconds, `storage` an optional object with `setItem` (default `window.localStorage`). It stores `{count, latest_id (0 if absent), ts: now}` as JSON under the key `admin_violation_toast_seen`. If the storage refuses (blocked, full or a private window) the error is caught and ignored, with the consequence that the toast simply repeats on the next page. Returns nothing. It overwrites the previous record, so only the last toast is remembered. Test: `writeSeen stores the count, newest id and time, and ignores blocked storage` in `static/tests/toast_notifications.test.js`.

### `shouldShowToast(seen, data, now)` [@ANCHOR: user_websites:js_toast_notifications_should_show_toast]

Exported pure function that decides whether the moderation toast is shown. `seen` is what `readSeen` returned (or `null`), `data` the endpoint's answer, `now` the time in milliseconds. It returns `false` when there is no data or `data.count` is not above zero. It returns `true` when nothing valid was seen before (no object or no numeric `ts`), when 12 hours (`MODERATION_TOAST_TTL_MS`) or more have passed since `seen.ts`, when the clock moved backwards (`now < seen.ts`), or when the queue grew: `data.count` is above the remembered count or `data.latest_id` is above the remembered newest id. Otherwise `false`, so a queue that shrank or stayed the same does not nag. No side effects. Test: `shouldShowToast: skip, increase and 12h expiry` in `static/tests/toast_notifications.test.js`.
