# Story: Owner Tools, Page Safety and Housekeeping

As a **Member** who edits my own site, I want my tools to explain what went wrong and never lose what I typed. As a **Visitor**, I want a member's page to be unable to run code or fetch from elsewhere. As an **Operator**, I want the background work of a busy site to be bounded and cheap.

## The Owner's Tools

* **Nothing typed is lost** `[@ANCHOR: user_websites:fn_owner_editor_with_error]`. When saving a page is refused, the editor is shown again with the reason and with everything the member typed (title, address, body and the published tick). The body is run through the member-HTML sanitizer again before it is put back, so a refused hostile body is never echoed raw. The same holds for the blog post form `[@ANCHOR: user_websites:fn_main_render_blog_post_editor]`, which shows the stored post normally and, after a refused save, the typed title, body and tick, with the reason and a 400 status. A post that has no owner sends the member back to their home page.
* **Finding a post** `[@ANCHOR: user_websites:fn_owner_own_post]`. A post is looked up for the site being managed, archived posts included so a deleted one can be restored. A post that does not exist, or that belongs to another member or group, is a 404, so the existence of someone else's post is not revealed.
* **Delete without JavaScript** `[@ANCHOR: user_websites:COMM_owner_delete_confirm]`. `GET /my/site/<slug>/<page|post>/<id>/delete` shows a confirmation page for a page or a post of the member's own site. It says that nothing is erased (the record is kept, archived, and can be restored). The dashboard shows the same question in a dialog. The deletion itself is a POST with a CSRF token. A deleted item is stamped `deleted_by_owner` `[@ANCHOR: user_websites:field_deleted_by_owner]`, a timestamp kept on both pages and posts, and the item stays hidden from every public surface and from the owner's lists until restored.
* **Undo and redo in the editor.** The rich editor keeps its own history, since it is a plain `contenteditable` area and not Odoo's backend editor. `recordHistory()` `[@ANCHOR: user_websites:rich_editor_record_history]` stores a snapshot of the content: typing within 700 ms of the last edit replaces the current snapshot, so a burst of typing is one undo step, while a toolbar action always starts a new one. History is capped at 200 snapshots, and nothing is stored if the content has not changed. `onInput()` `[@ANCHOR: user_websites:rich_editor_on_input]` records a snapshot and copies the editor into the hidden form field. `stepHistory(direction)` `[@ANCHOR: user_websites:rich_editor_step_history]` moves one snapshot back or forward, puts the cursor at the end and syncs the field. `onHistoryKey()` `[@ANCHOR: user_websites:rich_editor_history_key]` maps Ctrl or Cmd with Z to undo, with Shift+Z or with Y to redo, and ignores combinations that include Alt. `onBeforeInput()` `[@ANCHOR: user_websites:rich_editor_before_input]` sends the browser's own Undo and Redo menu items down the same path as the buttons.

## A Member's Page Cannot Run Code `[@ANCHOR: website_page_sanitize_arch]`

A member page's source is sanitized for everyone except administrators and the service account, on every create and write. Beyond the rules that remove scripts and frames:

* **Inline SVG** `[@ANCHOR: user_websites:page_arch_svg_allowlist]` is the one place a page can run script or fetch from elsewhere without a script tag (an animation that rewrites a link to `javascript:`, a style with `@import`, a `foreignObject` carrying HTML, a `use` of a `data:` URI, event handlers). Each `<svg>` block is rebuilt from the strict SVG allowlist in `zero_sudo`, with every template attribute and element removed inside it, or removed if it cannot be validated.
* **QWeb directives** `[@ANCHOR: user_websites:page_arch_qweb_allowlist]`. A member page may carry exactly two template directives: `t-name` with a plain name, and `t-call` naming one of four listed templates (the site layout, the default home template, and the two report-a-violation templates). Every other directive carries an expression the server would run under the viewer's account, and a blacklist on expression text is not a safe boundary, so all of them are removed and the removed value is kept in a `data-blocked-` attribute. Dangerous URL schemes (`javascript:`, `data:`, `vbscript:`, even when disguised with control characters) are removed from link and form attributes in the same way.
* **Text that is really markup** `[@ANCHOR: user_websites:page_arch_text_is_markup]`. QWeb writes static text into the page raw, so a text node that contains `<` (spelled as `&lt;script&gt;` or inside a CDATA section) would come out as a live element. Every `<` in text is re-spelled as the entity, which the browser shows as `<`. A second pass changes nothing, so saving again is stable.

## The Page Model's Own Guards

* **Creating** `[@ANCHOR: website_page_create]`. A page created without a name takes the name of its linked view. The caller's real create permission is checked, ownership is validated and filled in (a missing owner becomes the acting member) before the content is sanitized, so a violation report filed for stripped content names the right owner. Non-administrators cannot set a website on a page, because that would let a page escape its own site's isolation. Creation then runs as the service account, and the edge cache is invalidated.
* **Writing** `[@ANCHOR: website_page_write]`. The caller's write access and the ownership rules are checked, a non-administrator can write only an allowed list of fields, and changed source is sanitized. A content edit that spans pages of different owners is refused. Changes to the address or published state invalidate the cached page lookup once, and a re-entrant write caused by the published-state inverse does not repeat that.
* **Checking access** `[@ANCHOR: website_page_check_access]`. For write and unlink, a member of the user-websites group who is not an administrator must own the page or belong to the owning group, and otherwise gets an `AccessError` immediately. This stops Odoo's record-rule engine from writing a log line each time a member visits a public page and the frontend asks whether to show the Edit button. Group memberships are read once for the whole recordset.
* **Counting views** `[@ANCHOR: website_page_serve_page_view_counter]`. Serving a page increments a Redis counter for it, except for administrators. A Redis failure is logged and never fails the page view.
* **Flushing the counts** `[@ANCHOR: website_page_flush_redis_view_counters]`. A scheduled job moves the Redis counters into the database in batches of 1,000 keys. It walks the whole scan, subtracts each flushed amount atomically and deletes a key that reaches zero, skips zero values, and starts the next batch immediately only when a batch was full and this run drained at least one key. Earlier versions left drained keys at zero and restarted the scan every run, which made the job re-trigger itself about 500,000 times a day.

## Blog Posts

* **Sanitizing content** `[@ANCHOR: user_websites:blog_post_content_sanitize]`. A post's content field is not sanitized by the ORM, because the blog editor writes raw snippet markup. Member content is therefore run through Odoo's HTML sanitizer on create and write, which keeps a schematic as allowlisted SVG. Without this, any member could store script, event handlers or hostile SVG through JSON-RPC for every reader to receive.
* **Edge cache** `[@ANCHOR: user_websites:COMM_blog_post_invalidate_cloudflare_cache]`. After a post changes, a purge of the cache tag `site-<slug>` is queued for each affected website, grouped per website so that a purge from a context with no current website, such as a cron, still targets the post's own site. A failure to queue the purge is logged and never fails the member's own save.

## Groups

* **Creating a group** `[@ANCHOR: user_websites:COMM_group_create]`. A website group gets its own Odoo security group, named "Website Group: <name>", created as the user-websites service account and attached to the module's privilege when that record is present. A group created with an explicit `odoo_group_id` keeps it.
* **Suspension takes the content down in the background** `[@ANCHOR: user_websites:COMM_async_unpublish_group_content]`. Unpublishing a suspended group's pages and posts runs in a worker thread, so a large group does not hold a transaction open. It acquires its own registry and cursor, which are logged if they cannot be acquired, works one company at a time and in batches of 5,000 with a commit and a short pause between batches, and logs and survives any failure so the thread never dies silently.

## Reporting Content

* **Who reported** `[@ANCHOR: report_violation_records_logged_in_reporter]`. When a signed-in member files a report, their id is recorded on it. The id comes from the session and never from the posted form, so a reporter cannot name someone else. The public user is not a reporter.
* **Guest email field** `[@ANCHOR: report_violation_guest_email_field]`. The report form asks an anonymous visitor for an email address, stored as the report's `reported_by_email`. The condition is `website.is_public_user()`, which is the same visitor an edge-cached copy of the page is made for, so a cached page always carries the field. An earlier condition used a variable nothing ever set, so the field never appeared and guest reports carried no address.

## Capability Group for Ownership Bypass `[@ANCHOR: user_websites:ownership_bypass_group]`

The ownership checks of `user_websites.owned.mixin` skip their rules for system administrators, for user-websites administrators and for members of `group_user_websites_ownership_bypass`. That group is a pure capability: it carries no access rights, no record rules and no implied groups. The provisioning group implies it, so the provisioning account keeps passing. Other modules' service accounts hold only this group, instead of the whole provisioning group with its create, write and delete rights on groups, views, redirects and followers, which they had once joined only to get the one permission.

## Handing the GDPR Export to the Daemon

The data-export download is built by a separate daemon, so the web session hands over a single-use token.

* **Consuming a token** `[@ANCHOR: user_websites:COMM_gdpr_token_consume]`. `_consume(token)` marks a token used and returns the member it was issued for in one atomic `UPDATE ... WHERE consumed = false RETURNING`, so two concurrent callers cannot both succeed, and clears the cached `consumed` value because raw SQL bypasses the ORM cache. A missing or already used token is refused with the same message, so a caller without a valid token learns nothing about why. A token older than the expiry window is refused too, and is left marked used.
* **The one entry point** `[@ANCHOR: user_websites:COMM_gdpr_consume_and_export]`. `consume_and_export(token)` is what the daemon calls over RPC. It may be called only by the export daemon's own service account or a system administrator. It consumes the token, then reads the export as the scoped GDPR service account, drains every streamed generator into a list and returns one JSON-safe payload. It ties up one Odoo worker for the time it takes to build that payload; the fully batched alternative is described in the GDPR CSV export proposal.
