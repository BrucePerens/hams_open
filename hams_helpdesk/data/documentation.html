Hams Helpdesk (Verified)

This module has undergone a comprehensive review and repair cycle.

Hams Helpdesk provides Zero-Sudo compliant ticketing and issue tracking. It deeply integrates with the PagerDuty module via an agnostic Adapter API, allowing automated ticket creation and calendar event scheduling during system incidents.

"PagerDuty module" here means this platform's own Pager Duty module (pager_duty), not an outside paging service. Its adapter is "agnostic" because it does not import this module: it reads the name of the ticket model to create from the pager_duty.helpdesk_model system parameter (default hams_helpdesk.ticket). When an incident of high or critical severity is created, the adapter opens a ticket for it and, when an administrator is on duty, books a one-hour "Incident Response" calendar event for them (except for mail flagged as spam, described below). Low and medium severity incidents do not open a ticket on their own. The dependency runs one way: this module works without Pager Duty installed, but then no on-duty administrator is found and new tickets are left unassigned.

Zero-Sudo Architecture

This module strictly adheres to the Zero-Sudo mandate. Background operations, automated routing, and notifications are performed using dedicated service accounts:

  • Helpdesk Service Account: (hams_helpdesk.user_helpdesk_service) Posts assignment and shift notifications, executes handoffs, closes tickets for portal customers, and reads tickets for the customer portal. (The assignment itself is set when the ticket is created, by whoever creates it.)
  • PagerDuty Service Account: (pager_duty.user_pager_service_internal) Used by the Pager Duty module, not by this module, to create the "Incident Response" calendar event. The on-duty lookup itself runs as whoever creates the ticket.

Ticket Lifecycle

Tickets progress through stages: New, In Progress, Resolved, and Closed. Transitioning a ticket automatically notifies the reporting customer, when the ticket has a Customer set.

A fifth stage, Spam / Phishing (Quarantined), is used only for tickets the PagerDuty mail-ingestion adapter's own automated filter flagged as likely unsolicited commercial email or phishing when the inbound message first arrived. A quarantined ticket is never deleted or hidden -- it still appears in the ordinary Tickets list and in a dedicated "Spam / Phishing Review" menu, with the filter's own reasons recorded in both the ticket description and the linked PagerDuty incident's chatter, so a human can confirm the flag or move the ticket back to "New" if it was a real customer inquiry. No stage sends the customer-notification email when a ticket is created; that email is sent only by a later stage change. Pager Duty also creates these tickets with no Customer set, so a flagged sender is not emailed, since a flagged sender is, by design, not assumed to be a legitimate customer yet.

Formal Shift Handoff

Continuity is maintained via a formal handoff wizard. Operators are required to provide detailed briefing notes when transferring ownership, ensuring the next shift has all the necessary context to proceed with resolution.

Multi-Website Awareness & Security

The module is fully compatible with multi-website Odoo instances. Tickets are associated with the website where they were created. Portal users will only see tickets related to the website they are currently browsing, plus tickets not tied to any website (for example, ones created from email), ensuring strict data segregation between different web portals.

Access is strictly controlled via micro-privileges. Portal users can only view, message, and close their own tickets and are prohibited from modifying administrative fields such as Stage, Assignee, Priority, Customer, or Ticket Type.

Portal Access for Customers

Customers can access their tickets via the web portal. After logging in, they can see a list of their tickets, view the status of each ticket, and communicate with the helpdesk team by posting messages in the chatter. The ticket list is filtered based on the portal website to ensure privacy.

How to use the Helpdesk

Creating a Ticket

Tickets can be created from the Helpdesk menu in the backend. When a ticket is created, it is automatically assigned to the on-duty administrator if PagerDuty integration is active. The reporting customer is automatically subscribed to receive updates. If a ticket is created via a website portal, it is automatically tagged with that website and that website's company.

Customers create tickets from the portal at /my/tickets/new, choosing General Inquiry or "hams_local_relay: Bug / Security Report". Email sent to the admin or support address also becomes a ticket, linked to the sender's existing contact when there is one. GitHub security alerts and failed CI (continuous integration) runs can open tickets too, once the GitHub webhook secret is configured.

Managing a Ticket

Operators can move tickets through different stages (New, In Progress, Resolved, Closed). Each stage change (except a move into Spam / Phishing) triggers an automated email notification to the customer, keeping them informed about the progress. Critical incidents should be prioritized and moved to "In Progress" as soon as investigation begins. The "My Shift" menu lists your own New and In Progress tickets; Helpdesk Managers also have "Audit & Reporting", a pivot table of tickets by assignee and stage.

Executing a Handoff

To hand off a ticket to another operator, use the "Shift Handoff" button. This will open a wizard where you can select the next assignee and enter mandatory handoff notes. This ensures that no context is lost during shift changes. The handoff history is recorded in the ticket's chatter for audit purposes, as an internal note that the customer does not see. The button is hidden once a ticket is Resolved or Closed.

Closing a Ticket

Customers can close their own tickets from the portal once they are satisfied with the resolution. This is done by clicking the "Close Ticket" button on the ticket detail page. This action is logged in the chatter for transparency. Staff close a ticket with the "Close Ticket" button on the backend ticket form.

Child-Safety Mandatory Reports (NCMEC)

The ticket type "Child Safety: Apparent CSAM / Enticement / Trafficking (NCMEC Mandatory Report)" is for interactions flagged for the mandatory report to NCMEC's CyberTipline required by 18 U.S.C. Sec. 2258A. Portal customers cannot choose this type, and cannot change a ticket's type afterwards. When such a ticket is created:

  • Its priority is forced to Critical, and every Helpdesk Manager is subscribed and notified immediately, in addition to the normal on-duty assignment.
  • A report packet (the reported user, the recording's playback link, and the reporting contact) is assembled once and stored on the ticket, so later configuration changes cannot alter it.
  • A legal hold is attempted on the linked recording. If it does not succeed, the reason is shown on the ticket and an administrator can use "Apply Legal Hold Manually".

Only administrators see the NCMEC Report tab and its buttons. "Report to NCMEC" submits through NCMEC's reporting interface when an API address is configured (hams_helpdesk.ncmec_api_base_url, with its username and password). With no API address configured, it instead emails the packet to the configured fallback reporting contact and sets the status to "Emailed To Reporting Contact (Not Yet Filed With NCMEC)", which does not count as filed. "Mark Filed Manually" records that an administrator filed the packet through NCMEC's own portal. Once the status is Report Submitted or Report Confirmed, both actions refuse to run again, so the same incident cannot be filed twice. The two buttons are shown only while the status is Not Reported. The external AI triage account cannot read tickets of this type.
