# Story: Automatic Server-Exception Tickets

**[@ANCHOR: hams_helpdesk:exc_report_exception]**

Bruce asked that every Odoo exception result in a ticket. An administrator should find a new bug in
the Helpdesk before a member writes in, without a 10,000-hit storm filling the queue or a trace
leaking a member's data.

1.  **Where it hooks in.** `ir.http._handle_error` **[@ANCHOR: hams_helpdesk:exc_ir_http_handle_error]** sees every exception from a page controller and every JSON-RPC / ORM call from the web client; `report_request_exception()` **[@ANCHOR: hams_helpdesk:exc_report_request_exception]** reads only what needs no SQL (the failed request's cursor may be aborted). `ir.http._pre_dispatch` **[@ANCHOR: hams_helpdesk:exc_ir_http_pre_dispatch]** leaves werkzeug's route pattern for the fingerprint. `ir.cron._callback` **[@ANCHOR: hams_helpdesk:exc_ir_cron_callback]** reports a failed scheduled job (the mail queue runs as one, so a failure that escapes it is reported) and re-raises it unchanged. Not covered: a single mail that fails to send (Odoo records that on the mail itself and carries on) and failures inside external daemons such as the RabbitMQ consumers.
2.  **What is not reported.** `is_expected()` **[@ANCHOR: hams_helpdesk:exc_is_expected]**: not-found and other sub-500 HTTP errors (redirects, CSRF), failed logins, `UserError` / `ValidationError` shown to a member, `MissingError`, anonymous `AccessError`, an `AccessError` shown as a dialog by the web client, a vanished browser, scanner probes and bot user agents from anonymous callers. What is: an `AccessError` for a signed-in member on a page (the `/community` case), any RPC error, `KeyError` / `AttributeError` / `TypeError` / database errors, QWeb render errors, and every failure of a cron job.
3.  **Fingerprint.** `root_cause()` **[@ANCHOR: hams_helpdesk:exc_root_cause]** first looks through the wrappers `safe_eval` (every server-action and cron error) **[@ANCHOR: hams_helpdesk:exc_raised_in_safe_eval]** and QWeb put around the real error; `describe()` **[@ANCHOR: hams_helpdesk:exc_describe]** takes the exception type and the innermost frame inside an addon, by module name rather than file path; `normalize_route()` **[@ANCHOR: hams_helpdesk:exc_normalize_route]** uses the route pattern (never the raw path or a query string), keeping only `model.method` for web-client calls; `fingerprint()` **[@ANCHOR: hams_helpdesk:exc_fingerprint]** hashes the four parts.
4.  **Scrubbing.** `scrubbed_trace()` **[@ANCHOR: hams_helpdesk:exc_scrubbed_trace]** is built from the frames **[@ANCHOR: hams_helpdesk:exc_frame_lines]**, never from locals. The message is kept only for classes whose message comes from code (`AttributeError`, `TypeError`, ...) and then goes through `scrub_text()` **[@ANCHOR: hams_helpdesk:exc_scrub_text]**: emails, URLs with their queries, IP addresses, `password=` / `token=` / session / cookie pairs, bearer tokens, long tokens, callsigns and long digit runs are replaced. Every other class shows `<message withheld>`. The signed-in user is stored as an internal user id only.
5.  **Storm control.** `_admit()` **[@ANCHOR: hams_helpdesk:exc_admit]** lets a fingerprint through once a minute per process and the whole process 30 times a minute; refused hits are counted in memory and added by `_settle()` **[@ANCHOR: hams_helpdesk:exc_settle]** to the next write. Across workers, `_record_occurrence()` **[@ANCHOR: hams_helpdesk:exc_record_occurrence]** locks the row and refuses a write within a minute of the last. No more than 50 new tickets open in an hour; past that the row still counts and a later write opens the ticket.
6.  **Own cursor, never raises.** `_write_report()` **[@ANCHOR: hams_helpdesk:exc_write_report]** writes on `registry.cursor()` as the `exception_reporter_service_internal` account **[@ANCHOR: hams_helpdesk:exc_service_env]**, which can touch only `server_exception` tickets and the fingerprint rows. `report_exception()` swallows and logs any failure of its own on the `hams_helpdesk.exception_reporter` logger, and a thread-local flag stops it reporting itself.
7.  **The ticket.** `_sync_ticket()` **[@ANCHOR: hams_helpdesk:exc_sync_ticket]** opens or refreshes it; `_ticket_body()` **[@ANCHOR: hams_helpdesk:exc_ticket_body]** renders the counters and newest trace escaped. A closed ticket reopens only when `_release_marker()` **[@ANCHOR: hams_helpdesk:exc_release_marker]** (the newest module install or upgrade time) differs from the one at the last occurrence. The category is staff-only: no partner is set, the portal cannot choose it, the external AI triage account cannot read it, and it never wakes the triage daemon.
8.  **Back office.** Helpdesk > Server Exceptions **[@ANCHOR: hams_helpdesk:exc_fingerprint_list]** lists one row per failure with counts, filters (open, closed, recurring) and groupings (module, exception, source).
9.  **Mail failures (added later).** Odoo catches a single message that fails to send, records `state = 'exception'`, `failure_type` and `failure_reason` on the `mail.mail` and carries on, so the mail queue's cron job never fails. `mail.mail._postprocess_sent_message` **[@ANCHOR: hams_helpdesk:exc_mail_postprocess]** is the one place every such failure passes through (including a failed SMTP connection), and reports through `report_mail_failure()` **[@ANCHOR: hams_helpdesk:exc_report_mail_failure]** into the same pipeline, source "Outgoing / incoming mail", via `report_event()` **[@ANCHOR: hams_helpdesk:exc_report_event]** (the shared tail of `report_exception()`, for failures that have no Python exception to describe). The fingerprint is the failure type, a class label and the mail server id. The class label comes from a fixed vocabulary (`auth`, `tls`, `timeout`, `connect`, `temporary_4xx`, `permanent_5xx`, `other`) chosen by `mail_failure_class()` **[@ANCHOR: hams_helpdesk:exc_mail_failure_class]**; the failure text, recipients, subject and body are never read into the report, only counts. A mistyped address, a blacklisted or opted-out recipient and a duplicate are shown on the mail and are not tickets. A failure while processing an incoming bounce is reported from `mail.thread._routing_handle_bounce` **[@ANCHOR: hams_helpdesk:exc_mail_bounce]** and re-raised unchanged; it carries the exception class and frames, never the message. De-duplication and rate limits are the shared ones above.
10. **External daemons (added later).** A failure inside a daemon that runs outside Odoo under systemd (a RabbitMQ consumer, a sync or ingest program) is reported by `report_daemon_failure()` **[@ANCHOR: hams_helpdesk:exc_report_daemon_failure]**, an RPC only the exception reporter service account may call, over JSON-2 with the key the Daemon Key Manager issues to that account (`register_exception_reporter_key()` **[@ANCHOR: hams_helpdesk:register_exception_reporter_key]**). Callers: the systemd template unit `hams-exception-report@.service`, started by a daemon's `OnFailure=` drop-in, which sends the unit name, systemd's Result and the journal tail (`report_unit()` **[@ANCHOR: hams_helpdesk:daemon_report_unit]**, `post_report()` **[@ANCHOR: hams_helpdesk:daemon_post_report]**, `journal_tail()` **[@ANCHOR: hams_helpdesk:daemon_journal_tail]**, `unit_result()` **[@ANCHOR: hams_helpdesk:daemon_unit_result]**, `load_key()` **[@ANCHOR: hams_helpdesk:daemon_load_key]**), and `reporting_failures` **[@ANCHOR: hams_helpdesk:daemon_reporting_failures]** which a Python daemon wraps its consumer loop in (`report_exception()` **[@ANCHOR: hams_helpdesk:daemon_report_exception]** sends the class and frames from `frames_only()` **[@ANCHOR: hams_helpdesk:daemon_frames_only]**, never the message, then the exception is raised again). The unit name is validated by `daemon_unit_name()` **[@ANCHOR: hams_helpdesk:exc_daemon_unit_name]** and the journal tail scrubbed by `scrub_daemon_tail()` **[@ANCHOR: hams_helpdesk:exc_daemon_tail]** with the strict scrubber and an exception line cut to its class. It uses the same fingerprint, rate limits and own-cursor writer as every other source, with source "External daemon". Rust daemons use the OnFailure unit and may post the same request. See `daemon/README.md`.

11. **Not the request being reported (2026-10-12).** `_without_request()` **[@ANCHOR: hams_helpdesk:exc_without_request]** hides the ambient HTTP request while the report is written, so the writer runs as a cron job does. On production the assignment email's layout is rendered through QWeb, whose helpers read `request.env.user`; for a request whose session has no valid user that is an empty record and raised `Expected singleton: res.users()`, so the report was lost (four times that day, each on a login-only page). A failure of the writer is now logged with its traceback. `is_expected()` also drops `SessionExpiredException` (Odoo's redirect to the login page for a login-only page opened without a session) and the "No possible route found for incoming message" `ValueError` (inbound spam to an address nobody owns).
12. **Paging (2026-10-13).** Opening a ticket assigns it to the on-duty admin, which used to send two emails (Odoo's "You have been assigned" and the helpdesk's "Ticket Assigned") and a toast per ticket. Odoo's own email is now off for these tickets, and `_notification_state()` **[@ANCHOR: hams_helpdesk:exc_notification_state]** lets a new ticket page (one email, one toast) only when no ticket paged in the last `NOTIFY_WINDOW` (30 minutes), recorded in `notified_at` on the fingerprint row. Tickets opened inside the window are still created and assigned; the next one that pages says how many were silent.

*Verified by the tests in `hams_helpdesk/tests/test_exception_tickets.py`.*
