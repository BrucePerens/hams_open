# Story: Automatic Server-Exception Tickets

**[@ANCHOR: hams_helpdesk:exc_report_exception]**

Bruce asked that every Odoo exception result in a ticket. An administrator should find a new bug in
the Helpdesk before a member writes in, without a 10,000-hit storm filling the queue or a trace
leaking a member's data. Since 2026-10-23 Bruce also wants to write to the member who hit the error, to say the site team is on it (section 17).

1.  **Where it hooks in.** `ir.http._handle_error` **[@ANCHOR: hams_helpdesk:exc_ir_http_handle_error]** sees every exception from a page controller and every JSON-RPC / ORM call from the web client; `report_request_exception()` **[@ANCHOR: hams_helpdesk:exc_report_request_exception]** reads only what needs no SQL (the failed request's cursor may be aborted). `ir.http._pre_dispatch` **[@ANCHOR: hams_helpdesk:exc_ir_http_pre_dispatch]** leaves werkzeug's route pattern for the fingerprint. `ir.cron._callback` **[@ANCHOR: hams_helpdesk:exc_ir_cron_callback]** reports a failed scheduled job (the mail queue runs as one, so a failure that escapes it is reported) and re-raises it unchanged. Not covered: a single mail that fails to send (Odoo records that on the mail itself and carries on) and failures inside external daemons such as the RabbitMQ consumers.
2.  **What is not reported.** `is_expected()` **[@ANCHOR: hams_helpdesk:exc_is_expected]**: not-found and other sub-500 HTTP errors (redirects, CSRF), failed logins, `UserError` / `ValidationError` shown to a member, `MissingError`, anonymous `AccessError`, an `AccessError` shown as a dialog by the web client, a vanished browser, scanner probes and bot user agents from anonymous callers. What is: an `AccessError` for a signed-in member on a page (the `/community` case), any RPC error, `KeyError` / `AttributeError` / `TypeError` / database errors, QWeb render errors, and every failure of a cron job.
3.  **Fingerprint.** `root_cause()` **[@ANCHOR: hams_helpdesk:exc_root_cause]** first looks through the wrappers `safe_eval` (every server-action and cron error) **[@ANCHOR: hams_helpdesk:exc_raised_in_safe_eval]** and QWeb put around the real error; `describe()` **[@ANCHOR: hams_helpdesk:exc_describe]** takes the exception type and the innermost frame inside an addon, by module name rather than file path; `normalize_route()` **[@ANCHOR: hams_helpdesk:exc_normalize_route]** uses the route pattern (never the raw path or a query string), keeping only `model.method` for web-client calls; `fingerprint()` **[@ANCHOR: hams_helpdesk:exc_fingerprint]** hashes the four parts.
4.  **Scrubbing.** `scrubbed_trace()` **[@ANCHOR: hams_helpdesk:exc_scrubbed_trace]** is built from the frames **[@ANCHOR: hams_helpdesk:exc_frame_lines]**, never from locals. The message is kept only for classes whose message comes from code (`AttributeError`, `TypeError`, ...) and then goes through `scrub_text()` **[@ANCHOR: hams_helpdesk:exc_scrub_text]**: emails, URLs with their queries, IP addresses, `password=` / `token=` / session / cookie pairs, bearer tokens, long tokens, callsigns and long digit runs are replaced. Every other class shows `<message withheld>`. The signed-in user is stored as an internal user id only.
5.  **Storm control.** `_admit()` **[@ANCHOR: hams_helpdesk:exc_admit]** lets a fingerprint through once a minute per process and the whole process 30 times a minute; refused hits are counted in memory and added by `_settle()` **[@ANCHOR: hams_helpdesk:exc_settle]** to the next write. Across workers, `_record_occurrence()` **[@ANCHOR: hams_helpdesk:exc_record_occurrence]** locks the row and refuses a write within a minute of the last. No more than 50 new tickets open in an hour; past that the row still counts and a later write opens the ticket.
6.  **Own cursor, never raises.** `_write_report()` **[@ANCHOR: hams_helpdesk:exc_write_report]** writes on `registry.cursor()` as the `exception_reporter_service_internal` account **[@ANCHOR: hams_helpdesk:exc_service_env]**, which can touch only `server_exception` tickets and the fingerprint rows. `report_exception()` swallows and logs any failure of its own on the `hams_helpdesk.exception_reporter` logger, and a thread-local flag stops it reporting itself.
7.  **The ticket.** `_sync_ticket()` **[@ANCHOR: hams_helpdesk:exc_sync_ticket]** opens or refreshes it; `_ticket_body()` **[@ANCHOR: hams_helpdesk:exc_ticket_body]** renders the counters and newest trace escaped. A closed ticket reopens only when `_release_marker()` **[@ANCHOR: hams_helpdesk:exc_release_marker]** (the newest module install or upgrade time) differs from the one at the last occurrence. The category is staff-only: no partner is set, the portal cannot choose it, the external AI triage account cannot read it, and it never wakes the triage daemon.
8.  **Back office.** Helpdesk > Server Exceptions **[@ANCHOR: hams_helpdesk:exc_fingerprint_list]** lists one row per failure with counts, filters (open, closed, recurring) and groupings (module, exception, source).
9.  **Mail failures (added later).** Odoo catches a single message that fails to send, records `state = 'exception'`, `failure_type` and `failure_reason` on the `mail.mail` and carries on, so the mail queue's cron job never fails. `mail.mail._postprocess_sent_message` **[@ANCHOR: hams_helpdesk:exc_mail_postprocess]** is the one place every such failure passes through (including a failed SMTP connection), and reports through `report_mail_failure()` **[@ANCHOR: hams_helpdesk:exc_report_mail_failure]** into the same pipeline, source "Outgoing / incoming mail", via `report_event()` **[@ANCHOR: hams_helpdesk:exc_report_event]** (the shared tail of `report_exception()`, for failures that have no Python exception to describe). The fingerprint is the failure type, a class label and the mail server id. The class label comes from a fixed vocabulary (`auth`, `tls`, `timeout`, `connect`, `temporary_4xx`, `permanent_5xx`, `other`) chosen by `mail_failure_class()` **[@ANCHOR: hams_helpdesk:exc_mail_failure_class]**; the failure text, recipients, subject and body are never read into the report, only counts. A mistyped address, a blacklisted or opted-out recipient and a duplicate are shown on the mail and are not tickets. A failure while processing an incoming bounce is reported from `mail.thread._routing_handle_bounce` **[@ANCHOR: hams_helpdesk:exc_mail_bounce]** and re-raised unchanged; it carries the exception class and frames, never the message. De-duplication and rate limits are the shared ones above.
10. **External daemons (added later).** A failure inside a daemon that runs outside Odoo under systemd (a RabbitMQ consumer, a sync or ingest program) is reported by `report_daemon_failure()` **[@ANCHOR: hams_helpdesk:exc_report_daemon_failure]**, an RPC only the exception reporter service account may call, over JSON-2 with the key the Daemon Key Manager issues to that account (`register_exception_reporter_key()` **[@ANCHOR: hams_helpdesk:register_exception_reporter_key]**). Callers: the systemd template unit `hams-exception-report@.service`, started by a daemon's `OnFailure=` drop-in, which sends the unit name, systemd's Result and the journal tail (`report_unit()` **[@ANCHOR: hams_helpdesk:daemon_report_unit]**, `post_report()` **[@ANCHOR: hams_helpdesk:daemon_post_report]**, `journal_tail()` **[@ANCHOR: hams_helpdesk:daemon_journal_tail]**, `unit_result()` **[@ANCHOR: hams_helpdesk:daemon_unit_result]**, `load_key()` **[@ANCHOR: hams_helpdesk:daemon_load_key]**), and `reporting_failures` **[@ANCHOR: hams_helpdesk:daemon_reporting_failures]** which a Python daemon wraps its consumer loop in (`report_exception()` **[@ANCHOR: hams_helpdesk:daemon_report_exception]** sends the class and frames from `frames_only()` **[@ANCHOR: hams_helpdesk:daemon_frames_only]**, never the message, then the exception is raised again). The unit name is validated by `daemon_unit_name()` **[@ANCHOR: hams_helpdesk:exc_daemon_unit_name]** and the journal tail scrubbed by `scrub_daemon_tail()` **[@ANCHOR: hams_helpdesk:exc_daemon_tail]** with the strict scrubber and an exception line cut to its class. It uses the same fingerprint, rate limits and own-cursor writer as every other source, with source "External daemon". Rust daemons use the OnFailure unit and may post the same request. See `daemon/README.md`.

11. **Not the request being reported (2026-10-12).** `_without_request()` **[@ANCHOR: hams_helpdesk:exc_without_request]** hides the ambient HTTP request while the report is written, so the writer runs as a cron job does. On production the assignment email's layout is rendered through QWeb, whose helpers read `request.env.user`; for a request whose session has no valid user that is an empty record and raised `Expected singleton: res.users()`, so the report was lost (four times that day, each on a login-only page). A failure of the writer is now logged with its traceback. `is_expected()` also drops `SessionExpiredException` (Odoo's redirect to the login page for a login-only page opened without a session) and the "No possible route found for incoming message" `ValueError` (inbound spam to an address nobody owns).
12. **Paging (2026-10-13).** Opening a ticket assigns it to the on-duty admin, which used to send two emails (Odoo's "You have been assigned" and the helpdesk's "Ticket Assigned") and a toast per ticket. Odoo's own email is now off for these tickets, and `_notification_state()` **[@ANCHOR: hams_helpdesk:exc_notification_state]** lets a new ticket page (one email, one toast) only when no ticket paged in the last `NOTIFY_WINDOW` (30 minutes), recorded in `notified_at` on the fingerprint row. Tickets opened inside the window are still created and assigned; the next one that pages says how many were silent.

13. **One ticket per systemd unit.** Every report about one unit lands on one fingerprint row and so one ticket, whatever its kind or result: the OnFailure unit, a daemon's `reporting_failures`, and the pager checks that name the unit. `unit_key_parts()` **[@ANCHOR: hams_helpdesk:exc_unit_key_parts]** gives the fingerprint inputs they all share (the `unit_failed` / `exit-code` inputs a unit report always used, so a row and ticket opened before this keep counting); the report's own kind and result go in the sample trace, not the key. `_report_unit_failures()` **[@ANCHOR: hams_helpdesk:exc_report_unit_failures]** is how a pager check reports the units it says are failing (the pager's `report_incident` is the caller; Python only, so it is not on the RPC surface). It normalizes each name (a bare `odoo` means `odoo.service`), leaves out instances of a template unit (they would all collapse into one bogus row), reports through the same rate limits and own-cursor writer, and returns `{unit: ticket id}`, the id being False when no ticket exists (the new-ticket cap, or the write failed), so the caller then keeps its own ticket and a page is never lost to the de-duplication.
14. **Who reported it.** The ticket lists "Reported by": `_reporters()` **[@ANCHOR: hams_helpdesk:exc_reporters]** returns everything that has reported this failure, oldest first (empty for a row from before reporters were recorded). A reporter not listed yet is recorded at once; repeats are counted and written at most once a minute.
15. **When a closed ticket reopens.** `_reopen_reason()` **[@ANCHOR: hams_helpdesk:exc_reopen_reason]** gives the reason a recurrence reopens its closed ticket, or nothing when it stays closed and only counts. Three rules: a daemon or systemd unit failing again always reopens (a unit that fails after its ticket was closed is still broken); a release since the last occurrence; and a quiet period of 24 hours or more since the failure was last seen. `_announce_reopen()` **[@ANCHOR: hams_helpdesk:exc_announce_reopen]** posts the note on the reopened ticket ("Recurred ... reopened automatically", with the count and the reason). It pages the assignee as a new ticket would, under the same 30-minute window: inside the window of an earlier page it is a plain note.
16. **JavaScript errors in the browser (added 2026-10-21).** An uncaught error or unhandled promise rejection on a hams.com website, portal or back-office page becomes a ticket of the same kind, with source "Browser" and a name starting "Browser exception:". Scope: the website, portal and back-office bundles only (`web.assets_frontend`, `web.assets_backend`). The relay-served console (`shack_console`, `hams_local_relay`) loads neither bundle and reports nothing: reporting from software that runs on a member's own machine needs its own opt-in privacy decision, not made here.
    - **The reporter** (`browser_error_reporter.js`, started by `browser_error_reporter_boot.js`, both static files from the site's own origin, no inline script). `install()` **[@ANCHOR: hams_helpdesk:js_install]** listens for `error` and `unhandledrejection` beside Odoo's own error service (listeners do not hide each other's events); `onError()` **[@ANCHOR: hams_helpdesk:js_reporter_on_error]** and `onRejection()` **[@ANCHOR: hams_helpdesk:js_reporter_on_rejection]** pass the thrown value to `report()` **[@ANCHOR: hams_helpdesk:js_reporter_report]**, which never throws, never re-enters itself, sends each distinct error (type and top frame) once per page load, at most 5 per page load and at most one a second. `BrowserErrorReporter` **[@ANCHOR: hams_helpdesk:js_reporter_construct]** holds that state; `currentEnv()` **[@ANCHOR: hams_helpdesk:js_reporter_env]** and `pageEnv()` **[@ANCHOR: hams_helpdesk:js_page_env]** read the page's origin, path, browser and bundle scripts.
    - **What it sends**, built by `buildReport()` **[@ANCHOR: hams_helpdesk:js_build_report]**: the error class name; the message cut to 300 characters with any URL query removed by `stripUrlQueries()` **[@ANCHOR: hams_helpdesk:js_strip_url_queries]**; up to 8 stack frames as `url:line:col` from `reduceStack()` **[@ANCHOR: hams_helpdesk:js_reduce_stack]** (Chrome and Firefox/Safari formats, query and fragment dropped by `stripQuery()` **[@ANCHOR: hams_helpdesk:js_strip_query]**); the page route from `normalizeRoute()` **[@ANCHOR: hams_helpdesk:js_normalize_route]** (a segment with a digit or over 24 characters becomes `<x>`, no query string); the browser family from `agentFamily()` **[@ANCHOR: hams_helpdesk:js_agent_family]** (Firefox, Chrome, Edge, Safari, Opera or Other, never the user-agent string); and `bundle@version` from `releaseOf()` **[@ANCHOR: hams_helpdesk:js_release_of]**. It never sends form values, page text, a URL with a query string or anything about the user. `sendReport()` **[@ANCHOR: hams_helpdesk:js_send_report]** posts same-origin with `credentials: "same-origin"`, so the browser attaches its own session cookie, which only the server reads (section 17); the page adds no name, email or callsign. A failed send is ignored. `isIgnorable()` **[@ANCHOR: hams_helpdesk:js_is_ignorable]** skips what is not a bug in the page: Odoo's RPC errors (the server already ticketed the ones that matter), dropped connections and aborted requests, ResizeObserver notices and the information-free cross-origin "Script error."; an error whose top frame is not this site's own script (a browser extension, say) is not sent either.
    - **The endpoint** `POST /hams_helpdesk/browser_exception` **[@ANCHOR: hams_helpdesk:browser_exception_endpoint]** (`controllers/browser_exception_api.py`) answers with a status and no body: 204 recorded, held back or ignored (a sender cannot tell which), 400 invalid, 403 cross-site, 413 too large, 415 not JSON, 422 not a report of this site's own current scripts, 429 over the rate limit, 503 the limiter or the writer failed. Checks in order: `_is_same_origin()` **[@ANCHOR: hams_helpdesk:browser_same_origin]**; JSON content type; a declared body of at most 8 KiB; the per-visitor rate limit; then `parse_body()` **[@ANCHOR: hams_helpdesk:browser_parse_body]** (exactly the known keys, fixed types, no NUL byte); then `build_report()` **[@ANCHOR: hams_helpdesk:browser_build_report]**; then the bundle version check.
    - **Why it is safe to be `csrf=False`.** The endpoint does nothing on behalf of a session: it reads only the user id from the session cookie, to link a signed-in member's account to the ticket (section 17); a logged-out visitor has none and stays anonymous (no `member_ids`, `last_user_id` 0). Its only effect is an append-only write, by the exception reporter service account, of text that has been rebuilt from validated pieces. A cross-site request cannot carry the member's cookie into a report from a browser: the browser's own `Sec-Fetch-Site` and `Origin` headers refuse it (403), and a cross-site JSON POST needs a CORS preflight the endpoint never answers. When neither header is present (curl, an old browser) no session cookie of a member can be attached by another site either, and every other defence works without trusting the sender.
    - **Why not a nonce.** Odoo 19 has no CSP nonce support and the website's pages are cached by Odoo and Cloudflare, so a per-response nonce would be shared by every visitor and prove nothing. What the endpoint checks instead is cache-compatible: the report must name the **current** asset bundle version, `bundle@version`, one of the four page bundles. `_current_versions()` **[@ANCHOR: hams_helpdesk:browser_current_versions]** reads the versions Odoo computes for those bundles (a hash of their files, so it changes with every release, like a nonce that rotates per build; a worker keeps it for a minute) and `_release_is_current()` **[@ANCHOR: hams_helpdesk:browser_release_is_current]** refuses an unknown bundle or a stale version, which also drops reports from pages loaded before the last deploy. The top frame's own version must agree with the release.
    - **Only our own scripts.** `parse_frame()` **[@ANCHOR: hams_helpdesk:browser_parse_frame]** accepts a frame only when it is on the host the report was posted to and its path is an Odoo asset bundle (`/web/assets/<version>/<bundle>.min.js`) or a module's `static` script, with no query string, fragment, `..`, credentials or other scheme; a later foreign frame is dropped, a foreign top frame refuses the whole report. Extension, `blob:`, `data:` and other sites' scripts therefore never become tickets. The bundles are minified in production, so line and column point into the minified file; open the page with `?debug=assets` to map them.
    - **What is stored.** The type is `browser.<ErrorName>` and the module is the bundle or static module of the top frame. `stored_message()` **[@ANCHOR: hams_helpdesk:browser_stored_message]** keeps a message only for JavaScript's built-in error classes (TypeError, ReferenceError, RangeError, SyntaxError, EvalError, URIError), scrubbed with `scrub_text()` and cut to 300 characters; any other class shows `<message withheld>`. `is_ignorable()` **[@ANCHOR: hams_helpdesk:browser_is_ignorable]** repeats the client's noise filter, `agent_family()` **[@ANCHOR: hams_helpdesk:browser_agent_family]** accepts only the fixed browser families, and a User-Agent matching the bot list (`is_bot_agent()` **[@ANCHOR: hams_helpdesk:browser_is_bot_agent]**) is refused. The route is run through `normalize_route()` again. `frame_key()` **[@ANCHOR: hams_helpdesk:browser_frame_key]** drops the bundle version from the top frame for the fingerprint, which is the type, that frame (path, line, column) and the route, so a repeat on one release is one row; a new release moves the line and column, so the same bug may open a new ticket after a deploy.
    - **The same pipeline.** `_record()` **[@ANCHOR: hams_helpdesk:browser_record]** calls `report_event()` with source "browser" and the session's user id (None for a logged-out visitor), so the once-a-minute gate, the 30 writes a minute per process, the own-cursor writer, the row lock, the reopen rules and the 50 tickets an hour all apply. Browser reports have a cap of their own inside that one, `BROWSER_NEW_TICKETS_PER_HOUR` (10), so a flood of invented reports cannot use up the room for real server exceptions; past it the row is still counted. The ticket body says "Browser" as the source, says the signed-in member's account is linked to the report and that no form value, page text or query string is recorded, and shows the stack.
    - **Rate limit.** `_rate_limited()` **[@ANCHOR: hams_helpdesk:browser_rate_limited]** counts per visitor in Redis, 10 reports a minute and 60 an hour, keyed by a hash of the database name and the address Cloudflare reports (`_get_trusted_client_ip()`; behind the tunnel the socket address is always loopback). `_client_key()` **[@ANCHOR: hams_helpdesk:browser_client_key]** builds the key, which holds no address and expires on its own. If Redis cannot be reached the report is dropped, not accepted without limit. `MASTER_03` asks for edge rate limiting; the edge rules are listed in the module README and must be configured on hams1 and Cloudflare. The in-code limit is the second layer, as for the other public forms.

17. **Who to write to (added 2026-10-23).** Bruce's instruction: "tell me the user's name, callsign if any, and email. I want to write to them to tell them I am on the problem." This deliberately reverses the earlier default that a report carries no user.
    - **Who is identified.** For a page, an RPC call and a browser report only (`MEMBER_SOURCES`): the request's session user. `_reportable_member_uid()` **[@ANCHOR: hams_helpdesk:exc_reportable_member]** accepts an active account that is not the public user, OdooBot or a service account. A cron job, a mail the server could not send and an external daemon carry the job's own account, which is not an affected person, so they never link anyone. A logged-out visitor has no identity.
    - **Link, don't copy.** `_note_member()` **[@ANCHOR: hams_helpdesk:exc_note_member]** keeps one `hams_helpdesk.exception.member` row per (fingerprint, member): a many2one to `res.users` (`ondelete="set null"`), first and last seen, and the number of reports the member was part of (a lower bound: repeats held back by the once-a-minute gate cannot be told apart). The fingerprint has `last_member_id`, a link too. At most `MEMBER_LIST_LIMIT` (25) members are listed per failure, the rest are only counted in `unlisted_member_count`. A member the gate has not seen yet is admitted inside the once-a-minute window (like a new reporter), so two members hitting the same failure together are both listed. The name, callsign and email are never written into the description, a sample, a log line, a message or the fingerprint. (A many2many with counts is not possible, so the per-member model stands in for it.)
    - **What staff see.** The ticket form shows a "Reporting member(s)" panel (**[@ANCHOR: hams_helpdesk:ticket_member_panel]**, from `ticket.affected_member_ids`) with name, callsign(s), who to write to, email, first and last seen, and two buttons: "Email" (a `mailto:` link) and "Reply to member". The values are computed live by `_compute_details()` every time the ticket is read: the callsign is the account's own callsign plus the callbook rows linked to the account (read through the callbook's read-only service account, because helpdesk staff cannot read the callbook), and may be empty. The ticket list can show the member count and the latest member (`affected_member_count`, `latest_member_label`, **[@ANCHOR: hams_helpdesk:ticket_affected_members]**).
    - **Reply is a draft.** `action_reply_to_member()` **[@ANCHOR: hams_helpdesk:exc_reply_to_member]** opens the message composer on the ticket, addressed to the member and filled with a plain note that the site team is working on the problem. Nothing is sent until the staff member presses Send; the member is not made a follower. The note carries no route, no trace and no name.
    - **Minors.** `_contact_user()` **[@ANCHOR: hams_helpdesk:exc_contact_user]** is the extension point; here it always answers "the member". `ham_communications_consent` (hams_com) overrides it: a `child_supervised` account is written to through its active supervising guardian, labelled "Guardian of a minor member", and the minor's own email is never shown or used; with no active guardian link nobody is contacted ("withheld": no email and no buttons).
    - **Erasure.** Because the details are computed from the member's records, they follow them: an archived or erased account (the erasure chain deactivates it and rewrites its login) shows only "account closed"; a deleted account's link is set to null. The link rows themselves hold only an internal id and counts.
    - **Staff only.** Every field that shows the panel carries `groups` (helpdesk users and administrators), the member model's access rows give read to the same groups, and a portal member reading their own ticket gets none of it. The reporter, AI triage and GitHub webhook service accounts cannot read it.
    - **Nothing leaves the building.** No identity is in any text that is sent anywhere: not the ticket description (also used by the assignment email's ticket), not a message, not a log line, not a fingerprint, not a PagerDuty payload, not the daemon exception report (which carries only a unit name and a result). The Reply draft is the only outbound path, and a human presses Send. Tests: `test_exception_members.py`.
    - **Existing tickets** from before this release have no link and cannot be backfilled from the data; none was invented.

*Verified by the tests in `hams_helpdesk/tests/test_exception_tickets.py`, `hams_helpdesk/tests/test_exception_members.py` (and `ham_communications_consent/tests/test_helpdesk_exception_member.py` for minors), `hams_helpdesk/tests/test_browser_exceptions.py` and the others in that directory (with the Hoot suite `static/tests/browser_error_reporter.test.js`).*
