# Story: A Member's Data Export Includes Their Helpdesk Tickets

* **Story:** As a member, I want my data export to include the helpdesk tickets I filed. `res.users._get_gdpr_export_data` adds `helpdesk_tickets` (subject, description, callsign, type, stage, creation time) for tickets whose customer is my partner, read through the GDPR service account, so another member's ticket is never exported. Staff notes, triage fields and the thread are not included, and neither is a child-safety report (type csam_enticement_trafficking, or one naming a reported user or recording): those are held for the law and never handed to the account they concern. Tickets are kept on erasure (Bruce's decision, 2026-11-13): the thread holds staff replies and child-safety reports are held for the law, so erasure does not delete them -> [@ANCHOR: hams_helpdesk:res_users_get_gdpr_export_data]; checked by [@ANCHOR: hams_helpdesk:test_gdpr_export_is_own_tickets_only].

* **Class `ResUsersHelpdesk` (`models/res_users.py`):** the `_inherit = "res.users"` extension that carries the export hook above -> [@ANCHOR: hams_helpdesk:res_users_helpdesk]. It adds no fields and no database columns to `res.users`; it only overrides `_get_gdpr_export_data`, which calls `super` first so every other module's data stays in the export, then adds the `helpdesk_tickets` key when the member has tickets (at most 1000, `EXPORT_LIMIT`). Tickets are read as the GDPR service account (`zero_sudo.gdpr_service_internal`), never with `sudo`. Checked by [@ANCHOR: hams_helpdesk:test_gdpr_export_is_own_tickets_only].
